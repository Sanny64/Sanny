## Commands

Run commands from the repository root.

| Command                      | Purpose                                                                   |
| ---------------------------- | ------------------------------------------------------------------------- |
| `npm run check:backend`      | Run backend ESLint and TypeScript checks through the workspace.           |
| `npm run test:backend`       | Run backend unit and monitoring tests through the workspace.              |
| `npm run test:backend:redis` | Run the real-Redis session integration test; Docker is required.          |
| `npm run test`               | Run the complete root gate, including backend, frontend, and integration. |

Backend unit tests live in `backend/src/tests/`; monitoring integration tests live in `backend/monitoring/tests/`. These checks exercise backend behavior and do not run browser UI or accessibility tests.

The Redis check starts a disposable Docker Compose project using
`backend/docker/docker-compose.redis-test.yml`. Its app and Redis services inherit
the real Compose definitions, including the backend environment and TLS settings.
Redis must pass an authenticated TLS health check before tests start. The project
uses its own network and data/log volumes, publishes no ports, and removes its
containers and volumes afterward, including on failure. No running development
stack is required. Redis readiness is limited to ten health-check attempts, and
the test file has a 120-second timeout. `REDIS_CONNECT_TIMEOUT_MS` bounds initial
session-store connections (default 10000 milliseconds).

The root gate also requires installed Playwright browsers and a reachable development API/Auth0 tenant for live integration tests. Keep dedicated `TESTUSER_EMAIL` / `TESTUSER_PASSWORD` credentials for that integration suite; never use personal accounts.

## Test Boundaries

- **Backend:** `npm run check:backend` runs lint/types; `npm run test:backend` runs unit/monitoring tests; `npm run test:backend:redis` exercises session behavior against disposable real Redis services. The full root gate composes all three.
- **Frontend:** `npm run test:frontend` runs app lint/build, shared UI component tests, and mocked browser/accessibility checks. See [Frontend Automated Testing](../../frontend/local-testing/automated-testing.mdx).
- **Cross-system integration:** `npm run test:integration` exercises the connected apps, API, and live Auth0 password flow in the configured browsers. It is not a backend-only or frontend-only gate; Google automation is intentionally skipped.

A green `npm run test` shows that these configured checks passed for the current checkout and local test environment. The live flow covers the configured test identity and selected login/session/logout paths, not every provider, identity, account lifecycle, or deployment configuration. Mocked frontend checks verify UI behavior and request/response contracts only; they do not exercise backend persistence. Passing unit, monitoring, and Redis tests does not prove every branch, production workload, or failure mode.

The root gate does not build the documentation site or verify staging/production deployments. It also does not replace manual verification with the hosted Auth0 tenant, other identity providers, screen readers, complete keyboard-only workflows, or other assistive technology.
