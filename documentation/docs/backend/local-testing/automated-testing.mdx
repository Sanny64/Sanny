## Commands

Run commands from the repository root.

| Command                                     | Purpose                                                                   |
| ------------------------------------------- | ------------------------------------------------------------------------- |
| `npm run check:backend`                     | Run backend ESLint and TypeScript checks through the workspace.           |
| `npm run test:backend`                      | Run backend unit, monitoring, and Redis integration tests.                |
| `npm run test:integration:redis -w backend` | Run only the isolated Redis test; Docker is required.                     |
| `npm run test`                              | Run the complete root gate, including backend, frontend, and integration. |

Backend unit tests live in `backend/src/tests/`; monitoring integration tests live in `backend/monitoring/tests/`. These checks exercise backend behavior and do not run browser UI or accessibility tests.

The Redis check starts a disposable Docker Compose project using
`backend/docker/docker-compose.redis-test.yml`. It builds its own backend test image
and Redis service without loading `backend/.env` or extending runtime Compose
services. Its fixed test-only password is scoped to the internal Docker network.
The Redis TLS config and certificates are shared with the repository configuration.
Redis must pass an authenticated TLS health check before tests start. The project
uses its own network and data/log volumes, publishes no ports, and removes its
containers and data volume afterward, including on failure. No running development
stack is required. Redis readiness is limited to ten health-check attempts, and
the test file has a 120-second timeout. `REDIS_CONNECT_TIMEOUT_MS` bounds initial
session-store connections (default 10000 milliseconds).

The root gate also requires installed Playwright browsers and a reachable development API/Auth0 tenant for live integration tests. The live Playwright suite covers Chromium, Firefox, and Edge in one invocation. Keep dedicated `TESTUSER_EMAIL` / `TESTUSER_PASSWORD` credentials for that integration suite; never use personal accounts.

## Test Boundaries

- **Backend:** `npm run check:backend` runs lint/types; `npm run test:backend` runs unit, monitoring, and Redis integration tests. The Redis suite uses a disposable real Redis service.
- **Frontend:** `npm run test:frontend` runs app lint/build, shared UI component tests, and mocked browser/accessibility checks. See [Frontend Automated Testing](../../frontend/local-testing/automated-testing.mdx).
- **Cross-system integration:** `npm run test:e2e:real` exercises the connected apps, API, and live Auth0 password flow in Chromium, Firefox, and Edge in one invocation. It is not a backend-only or frontend-only gate; Google automation is intentionally skipped.

A green `npm run test` shows that these configured checks passed for the current checkout and local test environment. The live flow covers the configured test identity and selected login/session/logout paths, not every provider, identity, account lifecycle, or deployment configuration. Mocked frontend checks verify UI behavior and request/response contracts only; they do not exercise backend persistence. Passing unit, monitoring, and Redis tests does not prove every branch, production workload, or failure mode.

Both `test:ci` and the full root gate build documentation but do not verify hosted staging/production deployments. The CI gate needs Docker for isolated monitoring and Redis, not live Auth0 credentials; the full gate adds live authentication. Monitoring test rules are derived from production definitions in a temporary file; only timing is accelerated. These checks do not replace manual verification with other identity providers, screen readers, complete keyboard-only workflows, or other assistive technology.
