## Root Test Gates

Run commands from the repository root with Node.js 24 and npm 11.6.3.

- `npm run test:ci` runs formatting and static checks, contracts, backend and component tests, mocked browser tests, frontend and documentation builds, and Linux visual baselines. Docker and installed Playwright browsers are required; live Auth0 credentials are not.
- `npm run test` adds live Auth0 to `test:ci` and invokes the 429 spike scenario. That scenario skips unless `RUN_429_SPIKE_E2E=true`; enabling it also requires Grafana credentials and may trigger alerts. The gate requires a reachable development API/Auth0 tenant and dedicated test credentials. Google automation is intentionally skipped because Google may block controlled browsers.
- Before the live tests, `npm run test` checks `/healthcheck` on the API URL (`SANNY_E2E_API_URL`, `VITE_API_URL`, or `https://localhost:8443`). A running backend is reused; a stopped local backend is started with `npm run start:backend` and left running. Create a missing stack with `npm run restart:stack`.
- Docker test stacks (`sanny-monitoring-tests-<pid>` and `sanny-redis-tests-<pid>`) are removed when their runner finishes or is interrupted. Stacks left by a hard-killed runner are removed at the next start of that runner.

## Interpreting Results

A passing gate establishes that its configured checks passed for the current checkout and local test environment. Mocked frontend tests verify UI behavior and request/response contracts, not backend persistence or live Auth0. Live authentication covers only the configured test identity and selected flows. No local gate proves behavior for every browser, device, identity provider, input, or deployment configuration, and local results are not staging or production sign-off.

Automated test coverage does not replace manual checks with other identity providers, assistive technologies, or hosted security controls. Linux visual baselines are Chromium-only. The 429 spike behavior is not established by the latest full run because that test was skipped.

## Test Data and Evidence

Use isolated development or staging services and dedicated test identities. Never use personal accounts or record passwords, tokens, cookies, email addresses, or other personal data in test evidence. Record the date, build/revision, environment, browser/device or assistive technology, scenario, outcome, and residual issues in the restricted test record. Keep checks open until their evidence is recorded and reviewed.
