# Deployment

This project uses a simple release train for a monorepo with:

- `sanny` frontend.
- `auth` frontend.
- `documentation` site.
- Fastify backend.
- Shared packages under `shared/packages/**`.

The goal is to keep `main` very tidy (one commit per release), support a real web test environment, and keep the workflow easy to run for a solo developer.

---

## Branch model

This project uses `dev -> test -> main`.

This is the repository's documented release convention, not a branch-protection rule enforced by GitHub Actions. The workflows enforce their configured branch/path triggers but do not enforce pull-request or merge policy.

### `dev`

- Daily development branch.
- Feature work lands here first.
- Commit history can be messy and is never rewritten.
- No site is deployed from `dev`, and nothing in it is considered release-ready until it has been promoted to `test`.
- No deployment workflow is triggered by pushes to `dev`.

### `test`

- Release-candidate branch.
- Deploys the internet-accessible, Basic-Auth-protected test environment.
- Used to verify the exact release on the web before production.
- Fixes for release-candidate issues land here first.
- Keeps its full commit history and is never rewritten.

### `main`

- Production branch only.
- Kept clean and readable: exactly one commit per release.
- Never merged into. Every release commit is created from the file tree of `test` (see [Promote `test` to `main`](#5-promote-test-to-main)).
- Every release commit carries a tag in the form `release-1.0.0.x`.
- `main` and `test` intentionally do not share commit history. They only share identical file contents at release time.

## Deployment mapping

All test and production workflows depend on `.github/workflows/verify.yml`, the same secret-free verification gate used by pull requests. This includes tooling contracts and docs checks/builds, not just app builds. GitHub branch protection must separately require its result. Action references are pinned to commit SHAs and FTPS requires trusted hostname-matching certificates; there is no insecure certificate fallback.

Set repository variables `VITE_DEV_API_URL` and `VITE_PROD_API_URL` to the respective reachable HTTPS API origins. Test and production workflows pass their selected value as `VITE_API_URL`. Browser code uses only that canonical value. Local Vite development/test mode can still resolve the existing development input, and production mode the production input; explicit `VITE_API_URL` wins. Builds reject missing/invalid origins.

### Test environment

A push to `test` deploys the internet-accessible test environment with HTTP Basic Auth for website visitors.

- `sanny` -> `/public_html/testing/`, served at `https://test.sanny64.de/`.
- `auth` -> `/public_html/testing/auth/`, served at `https://test.auth.sanny64.de/`.
- `docs` -> `/public_html/testing/docs/`, served at `https://test.docs.sanny64.de/`, including both locales.
- `.github/workflows/deploy-to-test.yml` builds all three frontends and uploads each site with its own FTP sync-state file using the existing FTP secrets. Manual runs via `workflow_dispatch` are restricted to `test`.
- The nested directories are hosting document roots, not URL prefixes; all builds use `/`. Configure the subdomains and HTTPS in Hetzner. The workflow uses fixed FTP destinations: `/public_html/testing/`, `/public_html/testing/auth/`, and `/public_html/testing/docs/`.
- Set `TEST_BASIC_AUTH_ENTRY` to one or more newline-separated `username:hashed-password` lines. Each line creates a separate login, and every login works across all three sites. Do not include blank lines. The workflow generates `.htpasswd` from this secret and uploads it with the Sanny site. Set `TEST_BASIC_AUTH_FILE_PATH` to the absolute server filesystem path of `/public_html/testing/.htpasswd` (not its FTP-visible path). All three sites must be allowed to read this shared password file.
- Test builds set the asset and router base paths without changing production defaults. Apache rewrite rules support refreshing nested React routes.
- Shared packages are built as part of the frontend pipeline whenever relevant.
- The test workflow deploys only the frontend apps and documentation; it does not deploy the backend.

### Production

Docs deploy from `main` when `documentation/**`, `shared/packages/**`, `package.json`, or `package-lock.json` changes. Sanny and Auth deploy from `main` only when their configured paths change; the backend workflow runs for backend or workflow changes.

- `sanny` -> production site at `https://sanny64.de/`.
- `auth` -> production site at `https://auth.sanny64.de/`.
- `docs` -> production site at `https://docs.sanny64.de/`.
- Shared packages are built as part of the frontend pipeline whenever relevant.
- A push to `main` that changes `backend/**` or `.github/workflows/deploy-backend.yml` runs backend checks and builds the image once, publishing the same `latest` and commit-SHA tags to GHCR and Docker Hub (`sanny64/backend`). Docker Hub remains the image source for Gordon's analysis and for the VPS.
- A manual `workflow_dispatch` from `main` builds and publishes the image, then deploys that exact commit-SHA tag from Docker Hub to the VPS. Manual runs from other branches are skipped. Docker Hub credentials are configured as GitHub Actions secrets, not backend runtime variables.

## Shared packages rule

`shared/packages/**` always affects frontend builds.

That means:

- Any relevant change in `shared/packages/**` must trigger the frontend pipeline.
- Shared packages are not deployed manually on their own.
- If a shared package changes, the dependent frontend must rebuild in test and production.

This keeps shared code in sync with the apps that consume it.

## Release flow

### 1. Build work on `dev`

- Create a feature branch from `dev`.
  - `feat/<name>`
- Make your changes.
- Merge the feature branch back into `dev`.

### 2. Promote `dev` to `test`

- When you want a release candidate, merge `dev` into `test`.
- Push `test`.
- The test environment deploys automatically.

### 3. Test on the web

- Open the test environment in a browser.
- Verify UI, integration, deployment behavior, and any backend-dependent flows.
- Fix anything that fails by branching from `test`.

### 4. Fix release issues on `test`

- Create a fix branch from `test`.
  - `fix/<name>`
- Apply the fix.
- Merge the fix back into `test`.
- Push `test` again to redeploy the test environment.
- Once every fix is verified, merge `test` back into `dev` so both branches are on the same snapshot again.

### 5. Promote `test` to `main`

- Once the test environment is approved and `test` has been merged back into `dev`, create the release commit on `main`.
- The commit is built from the file tree of `test` with `git commit-tree`. This is not a merge, so it cannot cause merge conflicts, and none of the commits from `test` end up in `main`.
- The commit is tagged `release-1.0.0.x` and pushed together with `main`.

### 6. Production deploy

- After the push, production deploys from `main`.
- Frontends and docs deploy automatically.
- Backend deployment needs a manual `workflow_dispatch` trigger in the GitHub Actions menu.

## Step-by-step Git Guide

### Working on a feature

Create a feature branch based off the dev-branch:

```bash
git checkout dev
git pull origin dev
git checkout -b feat/<name>
```

Commit your work and push the branch:

```bash
git add .
git commit -m "Describe the change"
git push -u origin feat/<name>
```

When finished, merge it back into `dev`:

```bash
git checkout dev
git pull origin dev
git merge feat/<name>
git push origin dev
```

### Start a release candidate

When `dev` is ready to ship:

```bash
git checkout test
git pull origin test
git merge dev
git push origin test
```

This deploys the test environment.

### Test the release

Use the internet-accessible test site to verify:

- Layout and UI.
- Routing.
- API behavior.
- Shared package changes.
- Any deployment-specific issues.

If the release is good, move on to production. If not, fix it on `test`.

### Fix a problem found on `test`

Create a bug-fixing branch based off the test-branch:

```bash
git checkout test
git pull origin test
git checkout -b fix/<name>
```

Make the fix, then merge it back into `test`:

```bash
git add .
git commit -m "Fix release issue"
git checkout test
git pull origin test
git merge fix/<name>
git push origin test
```

Repeat for all bugs.
After every fix is validated on `test` and the release is fully stable, merge `test` into `dev`:

```bash
git checkout dev
git pull origin dev
git merge test
git push origin dev
```

### Promote to production

When `test` is approved and merged back into `dev`, create the release commit on `main`.

Replace `1.0.0.x` with the new version in all three places (Bash / Git Bash):

```bash
git fetch origin
git checkout main
git merge --ff-only origin/main
NEW=$(git commit-tree 'origin/test^{tree}' -p origin/main -m "Release 1.0.0.x")
git merge --ff-only "$NEW"
git tag release-1.0.0.x
git push origin main release-1.0.0.x
```

PowerShell variant:

```powershell
git fetch origin
git checkout main
git merge --ff-only origin/main
$NEW = git commit-tree "origin/test^{tree}" -p origin/main -m "Release 1.0.0.x"
git merge --ff-only $NEW
git tag release-1.0.0.x
git push origin main release-1.0.0.x
```

What the commands do:

- `git fetch origin` and `git merge --ff-only origin/main` bring your local `main` up to date and abort if it has diverged.
- `git commit-tree 'origin/test^{tree}' -p origin/main` creates one new commit containing exactly the files of `test`, with the previous `main` commit as its only parent. No commits from `test` are copied.
- `git merge --ff-only "$NEW"` moves `main` forward to that commit. Nothing is overwritten or force-pushed.
- The tag marks the release and is pushed together with `main`.

Verify the result. Both commands should show no difference:

```bash
git diff --stat origin/test main
git log --oneline -3 main
```

The first command must print nothing (identical file contents), and the log shows one release commit per version.

Notes:

- If `main` is protected on GitHub (pull request required), the direct push is rejected. Allow the push for your admin account or disable the rule for `main`.
- Pull requests and CI are intentionally not part of this step. Verification happens on the test environment before the release commit is created.
- If a release turns out to be wrong, fix it on `test` and create the next release. Do not rewrite `main`.

#### Example history

```text
main:  A -- R1 -- R2 -- R3                 (one commit per release, tagged)
test:  A -- a1 -- a2 -- ... -- a70 -- ...  (full history, never rewritten)
dev:   A -- a1 -- ... -- a70 -- d1 -- ...  (full history, never rewritten)
```

`R1`, `R2` and `R3` contain the same files that `test` had at the time of each release, but not its commits.

#### Hotfixes

Never change `main` directly. Every file change on `main` that is not on `test` is overwritten by the next release commit. Hotfixes follow the normal path: fix on `test` (branch `fix/<name>`), merge back into `dev`, then create the next release commit.

## Resync feature branches

If feature branches drift apart and you want them to share the same working state again, use `dev` as the integration point.

1. Merge all feature branches into `dev` locally (in dependency order to avoid conflicts).
2. Push `dev`.
3. On each feature branch, pull or merge `dev` to synchronize.
4. Push the updated feature branches.

This is a recovery step using the normal `dev` integration branch. It is useful when several branches depend on the same shared-package or workspace changes and you need local dev servers to work consistently again.

## Production deploy behavior

Production deploy starts from `main` after the release commit is pushed.

- `sanny`, `auth`, and the documentation site deploy from `main` when their workflow path filters match.
- Changes in shared packages trigger the frontend pipelines that include those paths.
- A push to `main` that changes backend files builds and publishes the same backend image to GHCR and Docker Hub; VPS deployment requires a manual `workflow_dispatch` run from `main`.

This makes `main` the source of truth for production while keeping the actual release history small and clean.

---

## Backend note

Backend deployment is separate from the frontend release train.

That means:

- The `test` branch workflow does not deploy the backend.
- A push to `main` that changes backend files builds and publishes the image to GHCR and Docker Hub but does not deploy it to the VPS.
- A manual `workflow_dispatch` run of `deploy-backend.yml` from `main` deploys the exact Docker Hub commit-SHA image and requires Docker Hub and VPS secrets plus a configured host.
- Frontend and docs releases should still follow the normal `dev -> test -> main` path regardless of backend status.
