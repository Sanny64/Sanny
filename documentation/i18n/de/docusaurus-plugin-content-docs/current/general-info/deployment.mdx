# Bereitstellung

Dieses Projekt verwendet einen einfachen Release-Zug für ein Monorepo mit:

- Frontend `sanny`.
- Frontend `auth`.
- Docusaurus-Dokumentationsseite.
- Fastify-Backend.
- Gemeinsam genutzten Paketen unter `shared/packages/**`.

Ziel ist es, `main` übersichtlich zu halten, eine echte Web-Testumgebung zu unterstützen und den Ablauf für eine einzelne entwickelnde Person einfach ausführbar zu machen.

---

## Branch-Modell

Dieses Projekt verwendet `dev -> test -> main`.

Dies ist die dokumentierte Release-Konvention des Repositorys, keine von GitHub Actions erzwungene Branch-Protection-Regel. Die Workflows erzwingen ihre konfigurierten Branch-/Pfad-Trigger, aber weder Pull-Requests noch Squash-Merges.

### `dev`

- Täglicher Entwicklungs-Branch.
- Feature-Arbeit landet zuerst hier.
- Die Commit-Historie kann unaufgeräumt sein.
- Die Commit-Historie wird niemals umgeschrieben.
- Von `dev` wird keine Website deployed und es werden keine Backend-Images gebaut oder veröffentlicht. Änderungen gelten erst dann als releasebereit, wenn sie nach `test` übernommen wurden.

### `test`

- Branch für Release-Kandidaten.
- Stellt die internet-erreichbare, durch Basic Auth geschützte Testumgebung bereit.
- Dient dazu, das konkrete Release vor der Produktion im Web zu prüfen.
- Fehlerbehebungen für den Release-Kandidaten landen zuerst hier.
- Die vollständige Commit-Historie bleibt erhalten und wird niemals umgeschrieben.

### `main`

- Ausschließlich für Produktion.
- Wird sauber und übersichtlich gehalten: genau ein Commit pro Release.
- Wird niemals gemergt. Jeder Release-Commit wird aus dem Dateibaum von `test` erstellt (siehe [„`test` nach `main` übernehmen“](#5-test-nach-main-übernehmen)).
- Jeder Release-Commit erhält einen Tag im Format `release-1.0.0.x`.
- `main` und `test` teilen absichtlich keine Commit-Historie. Zum Release-Zeitpunkt haben sie lediglich identische Datei-Inhalte.

## Zuordnung der Deployments

### Testumgebung

Ein Push nach `test` stellt die im Internet erreichbare Testumgebung mit HTTP Basic Auth für Website-Besucher bereit.

- `sanny` -> `/public_html/testing/`, erreichbar unter `https://test.sanny64.de/`.
- `auth` -> `/public_html/testing/auth/`, erreichbar unter `https://test.auth.sanny64.de/`.
- `docs` -> `/public_html/testing/docs/`, erreichbar unter `https://test.docs.sanny64.de/`, einschließlich beider Sprachen.
- `.github/workflows/deploy-to-test.yml` baut alle drei Frontends und lädt jede Website mit einer eigenen FTP-Synchronisationsdatei und den vorhandenen FTP-Secrets hoch. Manuelle Starts über `workflow_dispatch` sind auf `test` beschränkt.
- Die verschachtelten Verzeichnisse sind Dokumentenwurzeln beim Hoster, keine URL-Präfixe; alle Builds verwenden `/`. Subdomains und HTTPS müssen bei Hetzner eingerichtet werden. Vorhandene Repository-Variablen `TEST_SANNY_SERVER_DIR`, `TEST_AUTH_SERVER_DIR` oder `TEST_DOCS_SERVER_DIR` überschreiben diese Verzeichnisse.
- `TEST_BASIC_AUTH_ENTRY` enthält eine oder mehrere durch Zeilenumbrüche getrennte Zeilen im Format `benutzername:passwort-hash`. Jede Zeile legt einen eigenen Zugang an; alle Zugänge funktionieren auf allen drei Websites. Leerzeilen sind nicht erlaubt. Der Workflow erzeugt `.htpasswd` aus diesem Secret und lädt die Datei zusammen mit der Sanny-Website per FTP hoch. `TEST_BASIC_AUTH_FILE_PATH` enthält den absoluten Server-Dateisystempfad zur Datei `/public_html/testing/.htpasswd`, nicht den FTP-sichtbaren Pfad. Alle drei Websites müssen diese gemeinsame Passwortdatei lesen dürfen.
  Test-Builds setzen Asset- und Router-Basispfade, ohne die Produktions-Defaults zu ändern. Apache-Rewrite-Regeln unterstützen das Neuladen verschachtelter React-Routen.
  Gemeinsam genutzte Pakete werden bei Bedarf als Teil der Frontend-Pipeline gebaut.

#### Basic-Auth-Zugang erzeugen

Erzeuge mit Docker einen bcrypt-Passwort-Hash:

```powershell
docker run --rm -it httpd:2.4-alpine htpasswd -nB tester
```

Ersetze `tester` durch den gewünschten Benutzernamen und gib das Passwort ein, wenn du dazu aufgefordert wirst. `htpasswd` gibt die vollständige Zeile im Format `benutzername:hash` aus. Füge diese Zeile zu `TEST_BASIC_AUTH_ENTRY` hinzu. Für jeden Zugang kommt eine Zeile ohne Leerzeilen hinzu.

Der Workflow erstellt `.htpasswd` bei jedem Deployment neu aus `TEST_BASIC_AUTH_ENTRY`; vorhandene Einträge werden nicht angehängt. Kopiere daher vor dem Hinzufügen eines Zugangs alle bestehenden `benutzername:hash`-Zeilen aus der aktuellen `.htpasswd`-Datei in `TEST_BASIC_AUTH_ENTRY` und ergänze anschließend die neue Zeile. Andernfalls funktionieren die bisherigen Zugänge nicht mehr.

### Produktion

Ein Push nach `main` stellt die Produktionsumgebung bereit.

- `sanny` -> Produktionsseite unter `https://sanny64.de/`.
- `auth` -> Produktionsseite unter `https://auth.sanny64.de/`.
- `docs` -> Produktionsseite unter `https://docs.sanny64.de/`.
- Gemeinsam genutzte Pakete werden bei Bedarf als Teil der Frontend-Pipeline gebaut.
- Ein Push nach `main` führt Backend-Prüfungen aus und baut/veröffentlicht das Backend-Image. Pushes nach `dev` bauen oder veröffentlichen keine Backend-Images.
- Der VPS-Deployment-Job wird nur durch einen manuellen Start von `deploy-backend.yml` über `workflow_dispatch` ausgeführt.

## Regel für gemeinsam genutzte Pakete

Änderungen an `shared/packages/**` wirken sich immer auf Frontend-Builds aus.

Das bedeutet:

- Jede relevante Änderung in `shared/packages/**` muss die Frontend-Pipeline auslösen.
- Gemeinsam genutzte Pakete werden nicht eigenständig manuell deployed.
- Ändert sich ein gemeinsam genutztes Paket, müssen die davon abhängigen Frontends in Test- und Produktionsumgebung neu gebaut werden.

So bleibt gemeinsam genutzter Code mit den Apps synchron, die ihn verwenden.

## Release-Ablauf

### 1. Arbeit auf `dev`

- Erstelle einen Feature-Branch aus `dev`.
  - `feat/<name>`
- Nimm deine Änderungen vor.
- Führe den Feature-Branch wieder mit `dev` zusammen.

### 2. `dev` nach `test` übernehmen

- Wenn du einen Release-Kandidaten erstellen möchtest, merge `dev` nach `test`.
- Push nach `test`.
- Die Testumgebung wird automatisch deployed.

### 3. Im Web testen

- Öffne die Testumgebung in einem Browser.
- Prüfe UI, Integration, Deployment-Verhalten und alle vom Backend abhängigen Abläufe.
- Behebe Fehler, indem du von `test` aus einen Branch erstellst.

### 4. Release-Probleme auf `test` beheben

- Erstelle einen Fix-Branch aus `test`.
  - `fix/<name>`
- Nimm die Fehlerbehebung vor.
- Merge den Fix zurück nach `test`.
- Push erneut nach `test`, um die Testumgebung neu zu deployen.
- Sobald alle Fixes geprüft sind, merge `test` zurück nach `dev`, damit beide Branches wieder denselben Stand haben.

### 5. `test` nach `main` übernehmen

- Sobald die Testumgebung freigegeben und `test` zurück nach `dev` gemerged wurde, erstelle den Release-Commit auf `main` aus dem Dateibaum von `test`.
- Das ist kein Merge: Es entstehen keine Merge-Konflikte und keine Commits aus `test` werden nach `main` übernommen.
- Versehe den Release-Commit mit einem Tag im Format `release-1.0.0.x` und pushe beides zusammen.

### 6. Produktionsdeployment

- Nach dem Push des Release-Commits wird die Produktion von `main` aus deployed.
- Frontends und Docs werden automatisch deployed.
- Das Backend-Deployment muss im GitHub-Actions-Menü manuell über `workflow_dispatch` ausgelöst werden.

## Schritt-für-Schritt-Git-Anleitung

### An einem Feature arbeiten

Erstelle einen Feature-Branch auf Basis des Dev-Branches:

```bash
git checkout dev
git pull origin dev
git checkout -b feat/<name>
```

Committe deine Arbeit und pushe den Branch:

```bash
git add .
git commit -m "Describe the change"
git push -u origin feat/<name>
```

Wenn du fertig bist, merge den Branch zurück nach `dev`:

```bash
git checkout dev
git pull origin dev
git merge feat/<name>
git push origin dev
```

### Einen Release-Kandidaten starten

Wenn `dev` releasebereit ist:

```bash
git checkout test
git pull origin test
git merge dev
git push origin test
```

Dadurch wird die Testumgebung deployed.

### Das Release testen

Prüfe auf der öffentlichen Testseite:

- Layout und UI.
- Routing.
- API-Verhalten.
- Änderungen an gemeinsam genutzten Paketen.
- Deployment-spezifische Probleme.

Wenn alles funktioniert, fahre mit der Produktion fort. Andernfalls behebe den Fehler auf `test`.

### Ein auf `test` gefundenes Problem beheben

Erstelle einen Bugfix-Branch auf Basis von `test`:

```bash
git checkout test
git pull origin test
git checkout -b fix/<name>
```

Nimm die Fehlerbehebung vor und merge sie anschließend zurück nach `test`:

```bash
git add .
git commit -m "Fix release issue"
git checkout test
git pull origin test
git merge fix/<name>
git push origin test
```

Wiederhole dies für alle Fehler. Nachdem jeder Fix auf `test` geprüft wurde und das Release vollständig stabil ist, merge `test` nach `dev`:

```bash
git checkout dev
git pull origin dev
git merge test
git push origin dev
```

### Für die Produktion freigeben

Wenn `test` freigegeben und zurück nach `dev` gemerged ist, erstelle den Release-Commit auf `main` aus dem Dateibaum von `test`.

Ersetze `1.0.0.x` in allen drei Stellen durch die neue Version (Bash / Git Bash):

```bash
git fetch origin
git checkout main
git merge --ff-only origin/main
NEW=$(git commit-tree 'origin/test^{tree}' -p origin/main -m "Release 1.0.0.x")
git merge --ff-only "$NEW"
git tag release-1.0.0.x
git push origin main release-1.0.0.x
```

PowerShell-Variante:

```powershell
git fetch origin
git checkout main
git merge --ff-only origin/main
$NEW = git commit-tree "origin/test^{tree}" -p origin/main -m "Release 1.0.0.x"
git merge --ff-only $NEW
git tag release-1.0.0.x
git push origin main release-1.0.0.x
```

`git commit-tree` erstellt einen einzelnen Commit mit exakt dem Dateibaum von `test` und `origin/main` als einzigem Vorgänger. Es werden keine Commits aus `test` übernommen. `git merge --ff-only` bewegt `main` auf diesen Commit, ohne Dateien zu überschreiben oder einen Force-Push zu benötigen. Der Tag kennzeichnet das Release und wird zusammen mit `main` gepusht.

Prüfe anschließend das Ergebnis:

```bash
git diff --stat origin/test main
git log --oneline -3 main
```

Der erste Befehl darf nichts ausgeben, da beide Branches denselben Datei-Inhalt haben müssen. Die Log-Ausgabe zeigt einen Release-Commit pro Version.

Falls `main` auf GitHub geschützt ist und Pull Requests verlangt, wird der direkte Push abgelehnt. Erlaube den Push für dein Admin-Konto oder deaktiviere die Regel für `main`. Pull Requests und CI sind nicht Teil dieses Schritts; die Prüfung erfolgt vorher auf der Testumgebung. Falls ein Release fehlerhaft ist, behebe den Fehler auf `test` und erstelle das nächste Release. Schreibe `main` nicht um.

#### Beispielhistorie

```text
main:  A -- R1 -- R2 -- R3                 (ein getaggter Commit pro Release)
test:  A -- a1 -- a2 -- ... -- a70 -- ...  (vollständige Historie, nie umgeschrieben)
dev:   A -- a1 -- ... -- a70 -- d1 -- ...  (vollständige Historie, nie umgeschrieben)
```

`R1`, `R2` und `R3` enthalten jeweils dieselben Dateien wie `test` zum Zeitpunkt des Releases, aber nicht dessen Commits.

#### Hotfixes

Ändere `main` niemals direkt. Jede Änderung auf `main`, die nicht in `test` enthalten ist, wird beim nächsten Release-Commit überschrieben. Hotfixes folgen dem normalen Ablauf: Fehler auf `test` beheben, nach `dev` zurückmergen und anschließend den nächsten Release-Commit erstellen.

## Feature-Branches synchronisieren

Wenn Feature-Branches auseinanderlaufen und wieder denselben Arbeitsstand verwenden sollen, nutze `dev` als Integrationspunkt.

1. Merge alle Feature-Branches lokal nach `dev` (in Abhängigkeitsreihenfolge, um Konflikte zu vermeiden).
2. Pushe `dev`.
3. Hole auf jedem Feature-Branch die Änderungen aus `dev` oder merge `dev`, um ihn zu synchronisieren.
4. Pushe die aktualisierten Feature-Branches.

Dies ist ein Wiederherstellungsschritt über den normalen Integrations-Branch `dev`. Er ist hilfreich, wenn mehrere Branches von denselben Änderungen an gemeinsam genutzten Paketen oder Workspaces abhängen und lokale Entwicklungsserver deshalb wieder konsistent laufen müssen.

---

## Verhalten des Produktionsdeployments

Das Produktionsdeployment startet, nachdem der Release-Commit nach `main` gepusht wurde.

- `sanny`, `auth` und die Dokumentationsseite werden von `main` deployed, wenn ihre Workflow-Pfadfilter zutreffen.
- Änderungen an gemeinsam genutzten Paketen lösen die Frontend-Workflows aus, die diese Pfade enthalten.
- Ein Push nach `main` baut und veröffentlicht das Backend-Image.
- Für das VPS-Deployment ist ein manueller Start per `workflow_dispatch` in Github erforderlich.

Damit bleibt `main` die maßgebliche Quelle für Produktion und die eigentliche Release-Historie dennoch klein.

---

## Hinweis zum Backend

Das Backend-Deployment ist vom Frontend-Release-Ablauf getrennt.

Das bedeutet:

- Der Test-Workflow für `test` deployed das Backend nicht.
- Ein Push nach `main` baut und veröffentlicht das Backend-Image, deployed es aber nicht auf den VPS.
- Ein manueller Start von `deploy-backend.yml` über `workflow_dispatch` führt das VPS-Deployment aus und benötigt konfigurierte Secrets sowie einen eingerichteten Host.
- Frontend- und Docs-Releases sollten unabhängig vom Backend-Status weiterhin dem normalen Ablauf `dev -> test -> main` folgen.
