## Befehle

Alle Befehle im Repository-Stammverzeichnis ausführen.

| Befehl                       | Zweck                                                                  |
| ---------------------------- | ---------------------------------------------------------------------- |
| `npm run test:backend`       | Backend-Typprüfung sowie Backend-Unit- und Monitoring-Tests ausführen. |
| `npm run test:backend:redis` | Redis-Session-Integration ausführen; Docker ist erforderlich.          |
| `npm run test`               | Vollständiges Root-Gate für Backend, Frontend und Integration starten. |

Backend-Unit-Tests liegen in `backend/src/tests/`; Monitoring-Integrationstests liegen in `backend/monitoring/tests/`. Diese Prüfungen testen Backend-Verhalten und führen keine Browser-UI- oder Accessibility-Tests aus.

Der Redis-Test startet ein isoliertes Docker-Compose-Projekt mit
`backend/docker/docker-compose.redis-test.yml`. Die Dienste `app` und `redis`
übernehmen die Konfiguration aus den regulären Compose-Definitionen, einschließlich
Backend-Umgebung und TLS-Einstellungen. Redis muss vor Testbeginn einen
authentifizierten TLS-Healthcheck bestehen. Das Projekt verwendet ein eigenes
Netzwerk und eigene Daten- und Log-Volumes, veröffentlicht keine Ports und entfernt
Container sowie Volumes auch bei einem Fehler. Ein laufender Entwicklungs-Stack ist
nicht erforderlich. Die Redis-Bereitschaft wird höchstens zehnmal geprüft; für die
Testdatei gilt ein Timeout von 120 Sekunden. `REDIS_CONNECT_TIMEOUT_MS` begrenzt
Verbindungen des Sitzungs-Stores beim Start (Standardwert: 10000 Millisekunden).

Das Root-Gate benötigt außerdem installierte Playwright-Browser und eine erreichbare
Entwicklungs-API sowie einen Auth0-Tenant für Live-Integrationstests. Verwende dafür
dedizierte Zugangsdaten `TESTUSER_EMAIL` / `TESTUSER_PASSWORD`, niemals persönliche
Konten.

## Testgrenzen

- **Backend:** `npm run test:backend` prüft Backend-Typen und führt Unit-/Monitoring-Tests aus; `npm run test:backend:redis` testet Sitzungsabläufe mit isolierten, echten Redis-Diensten.
- **Frontend:** `npm run test:frontend` führt App-Lint/Build, gemeinsame UI-Komponententests sowie gemockte Browser- und Accessibility-Prüfungen aus. Siehe [Automatisierte Frontend-Tests](../../frontend/local-testing/automated-testing.mdx).
- **Systemübergreifende Integration:** `npm run test:integration` prüft verbundene Apps, API und den Live-Auth0-Passwort-Flow in den konfigurierten Browsern. Dies ist kein reines Backend- oder Frontend-Gate; Google-Automatisierung wird absichtlich übersprungen.

Ein erfolgreiches `npm run test` zeigt, dass diese konfigurierten Prüfungen für den aktuellen Checkout und die lokale Testumgebung bestanden wurden. Der Live-Flow prüft die konfigurierte Testidentität und ausgewählte Login-/Sitzungs-/Logout-Abläufe, nicht jeden Anbieter, jede Identität, jeden Kontenlebenszyklus oder jede Deployment-Konfiguration. Gemockte Frontend-Browsertests prüfen nur UI-Verhalten und Request-/Response-Verträge; sie greifen nicht auf die Backend-Persistenz zu. Erfolgreiche Unit-, Monitoring- und Redis-Tests belegen nicht jeden Codepfad, Produktionslastfall oder Fehlerzustand.

Das Root-Gate baut weder die Dokumentationswebsite noch verifiziert es Staging-/Produktionsdeployments. Es ersetzt auch keine manuelle Prüfung mit dem gehosteten Auth0-Tenant, anderen Identitätsanbietern, Screenreadern, vollständigen Tastaturabläufen oder weiterer assistiver Technologie.
