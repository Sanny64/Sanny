## Befehle

Alle Befehle im Repository-Stammverzeichnis ausführen.

| Befehl                                      | Zweck                                                                  |
| ------------------------------------------- | ---------------------------------------------------------------------- |
| `npm run check:backend`                     | Backend-ESLint und TypeScript-Prüfung über das Workspace ausführen.    |
| `npm run test:backend`                      | Backend-Unit-, Monitoring- und Redis-Integrationstests ausführen.      |
| `npm run test:integration:redis -w backend` | Nur den isolierten Redis-Test ausführen; Docker ist erforderlich.      |
| `npm run test`                              | Vollständiges Root-Gate für Backend, Frontend und Integration starten. |

Backend-Unit-Tests liegen in `backend/src/tests/`; Monitoring-Integrationstests liegen in `backend/monitoring/tests/`. Diese Prüfungen testen Backend-Verhalten und führen keine Browser-UI- oder Accessibility-Tests aus.

Der Redis-Test startet ein isoliertes Docker-Compose-Projekt mit
`backend/docker/docker-compose.redis-test.yml`. Es baut ein eigenes Backend-Testimage
und einen Redis-Dienst, ohne `backend/.env` zu laden oder Laufzeit-Compose-Dienste
zu erweitern. Das feste Testpasswort ist auf das interne Docker-Netzwerk begrenzt.
Redis-TLS-Konfiguration und -Zertifikate stammen aus der Repository-Konfiguration.
Redis muss vor Testbeginn einen
authentifizierten TLS-Healthcheck bestehen. Das Projekt verwendet ein eigenes
Netzwerk und ein Daten-Volume, veröffentlicht keine Ports und entfernt Container
sowie Volume auch bei einem Fehler. Ein laufender Entwicklungs-Stack ist
nicht erforderlich. Die Redis-Bereitschaft wird höchstens zehnmal geprüft; für die
Testdatei gilt ein Timeout von 120 Sekunden. `REDIS_CONNECT_TIMEOUT_MS` begrenzt
Verbindungen des Sitzungs-Stores beim Start (Standardwert: 10000 Millisekunden).

Das Root-Gate benötigt außerdem installierte Playwright-Browser und eine erreichbare
Entwicklungs-API sowie einen Auth0-Tenant für Live-Integrationstests. Die Live-Playwright-Suite
deckt Chromium, Firefox und Edge in einem Aufruf ab. Verwende dafür
dedizierte Zugangsdaten `TESTUSER_EMAIL` / `TESTUSER_PASSWORD`, niemals persönliche
Konten.

## Testgrenzen

- **Backend:** `npm run check:backend` führt Lint und Typprüfung aus; `npm run test:backend` führt Unit-, Monitoring- und Redis-Integrationstests aus. Die Redis-Suite verwendet einen isolierten echten Redis-Dienst.
- **Frontend:** `npm run test:frontend` führt App-Lint/Build, gemeinsame UI-Komponententests sowie gemockte Browser- und Accessibility-Prüfungen aus. Siehe [Automatisierte Frontend-Tests](../../frontend/local-testing/automated-testing.mdx).
- **Systemübergreifende Integration:** `npm run test:e2e:real` prüft verbundene Apps, API und den Live-Auth0-Passwort-Flow in Chromium, Firefox und Edge in einem Aufruf. Dies ist kein reines Backend- oder Frontend-Gate; Google-Automatisierung wird absichtlich übersprungen.

Ein erfolgreiches `npm run test` zeigt, dass diese konfigurierten Prüfungen für den aktuellen Checkout und die lokale Testumgebung bestanden wurden. Der Live-Flow prüft die konfigurierte Testidentität und ausgewählte Login-/Sitzungs-/Logout-Abläufe, nicht jeden Anbieter, jede Identität, jeden Kontenlebenszyklus oder jede Deployment-Konfiguration. Gemockte Frontend-Browsertests prüfen nur UI-Verhalten und Request-/Response-Verträge; sie greifen nicht auf die Backend-Persistenz zu. Erfolgreiche Unit-, Monitoring- und Redis-Tests belegen nicht jeden Codepfad, Produktionslastfall oder Fehlerzustand.

Das Root-Gate baut beide Dokumentationssprachen, verifiziert aber keine gehosteten Staging-/Produktionsdeployments. Es ersetzt keine manuelle Prüfung mit weiteren Identitätsanbietern, Screenreadern, vollständigen Tastaturabläufen oder weiterer assistiver Technologie.
