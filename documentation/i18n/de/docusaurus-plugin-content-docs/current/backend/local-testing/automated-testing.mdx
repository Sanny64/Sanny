## Befehle

Alle Befehle im Repository-Stammverzeichnis ausführen. Gemeinsame Anforderungen der Root-Gates, das Ergebnis des letzten vollständigen Laufs und allgemeine Grenzen stehen im [Leitfaden zu lokalen Tests](../../general-info/testing.mdx).

| Befehl                                      | Zweck                                                                       |
| ------------------------------------------- | --------------------------------------------------------------------------- |
| `npm run check:backend`                     | Backend-ESLint und TypeScript-Prüfung über das Workspace ausführen.         |
| `npm run test:backend`                      | Backend-Unit-, Monitoring-, Redis- und Discord-Integrationstests ausführen. |
| `npm run test:integration:redis -w backend` | Nur den isolierten Redis-Test ausführen; Docker ist erforderlich.           |

Backend-Unit-Tests liegen in `backend/src/tests/`; Monitoring-Integrationstests liegen in `backend/monitoring/tests/`. Diese Prüfungen testen Backend-Verhalten und führen keine Browser-UI- oder Accessibility-Tests aus.

Der Redis-Test startet ein isoliertes Docker-Compose-Projekt mit `backend/docker/docker-compose.test.redis.yml`. Es baut ein eigenes Backend-Testimage und einen Redis-Dienst, ohne `backend/.env` zu laden oder Laufzeit-Compose-Dienste zu erweitern. Das feste Testpasswort ist auf das interne Docker-Netzwerk begrenzt. Die Redis-TLS-Konfiguration wird gemeinsam verwendet; der Runner erzeugt jedoch eine eigene eintägige Test-CA und ein Redis-Zertifikat in einem temporären Verzeichnis. Entwicklerzertifikate werden nicht eingebunden; OpenSSL auf dem Host ist nicht erforderlich. Die temporären Zertifikate werden nach dem Compose-Teardown entfernt. Redis muss vor Testbeginn einen authentifizierten TLS-Healthcheck bestehen. Das Projekt verwendet ein eigenes Netzwerk und ein Daten-Volume, veröffentlicht keine Ports und entfernt Container sowie Volume auch bei einem Fehler. Ein laufender Entwicklungs-Stack ist nicht erforderlich. Die Redis-Bereitschaft wird höchstens zehnmal geprüft; für die Testdatei gilt ein Timeout von 120 Sekunden. `REDIS_CONNECT_TIMEOUT_MS` begrenzt Verbindungen des Sitzungs-Stores beim Start (Standardwert: 10000 Millisekunden).

Das Root-Gate benötigt außerdem installierte Playwright-Browser und eine erreichbare Entwicklungs-API sowie einen Auth0-Tenant für Live-Integrationstests. Die Live-Playwright-Suite deckt Chromium, Firefox und Edge in einem Aufruf ab. Verwende dafür dedizierte Zugangsdaten `TESTUSER_EMAIL` / `TESTUSER_PASSWORD`, niemals persönliche Konten.

## Testgrenzen

- **Backend:** `npm run check:backend` führt Lint und Typprüfung aus; `npm run test:backend` führt Unit-, Monitoring-, Redis- und Discord-Integrationstests aus. Die Redis-Suite verwendet einen isolierten echten Redis-Dienst.
- **Frontend:** `npm run test:e2e:mocked` führt gemockte Browser- und Accessibility-Prüfungen aus; `npm run build:frontend` erstellt beide Apps und die Dokumentation. Siehe [Automatisierte Frontend-Tests](../../frontend/local-testing/automated-testing.mdx).
- **Systemübergreifende Integration:** `npm run test:e2e:real` prüft verbundene Apps, API und den Live-Auth0-Passwort-Flow in Chromium, Firefox und Edge in einem Aufruf. Dies ist kein reines Backend- oder Frontend-Gate; Google-Automatisierung wird absichtlich übersprungen.

Erfolgreiche Backend-Unit-, Monitoring- und Redis-Tests belegen nicht jeden Codepfad, Produktionslastfall oder Fehlerzustand. Monitoring-Testregeln werden temporär aus den Produktionsdefinitionen abgeleitet; nur das Timing wird beschleunigt. Gemeinsame Aussagekraft und Grenzen der Root-Gates stehen im [Leitfaden zu lokalen Tests](../../general-info/testing.mdx).
