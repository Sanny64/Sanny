# Backend

Install with root `npm ci` using Node 24/npm 11 and the root lockfile. Build from the repository root with `docker build -f apps/backend/docker/Dockerfile .`; `npm run build:backend` builds only. Production Compose inherits common services from the development file, and Alloy replaces Promtail. Follow the [workspace migration guide](../apps/documentation/docs/general-info/tooling.mdx) before deployment.

## Docker naming

The development Compose image is `sanny64-backend:latest`, and the runtime container is `sanny64-backend`. Production uses the same container name but keeps the deployed registry image `sanny64/backend:<tag>`. Test projects retain generated names and independent images. Fixed runtime container names permit only one instance per Docker host, so do not run development and production stacks concurrently on that host. Run root `npm run initialize:stack` to rebuild buildable images and recreate the full development Compose stack; it delegates to the workspace `initialize:stack` script. Use `npm run restart:backend` to rebuild and recreate only the backend service. Both preserve volumes. `build:backend` builds the backend image without recreating containers. The old image tag is not automatically deleted.

## Account linking

Google/password identity conflicts require confirmation and authentication of
the other identity through the auth frontend. The OAuth callback restarts Auth0
authorization once for an unresolved Google/password conflict, preserving the
return destination and email-MFA requirement. It does not create a session or
merge users before Auth0 proves the link. If the retry still returns unlinked
identities, it redirects to the auth error page rather than looping.

Deploy `auth0/post-login/linkAccounts.js` to the Auth0 **Login** flow as well as
deploying the backend; the repository copy is not executed by the backend.
Pending or confirmed metadata must not suppress confirmation for identities
that are still unlinked. Proof logins (`link_proof=true`) still bypass the
linking prompt. Configure the development Action with `NODE_ENV=development`
and `<env>_ACCOUNT_LINK_CONFIRMATION_URL` pointing to the backend's
`/api/v001/auth/confirm-account-linking` endpoint (not directly to the frontend).
The backend's `<env>_ACCOUNT_LINK_FRONTEND_URL` points to the auth frontend's
`/confirm-linking` page.

## Automated testing

Backend tests live in `src/tests/`: `sanny64/` groups application tests into `auth/`, `auth0/`, `sessions/`, `users/`, `security/`, and `observability/`. The manual proxy check belongs to `sanny64/security/`. `grafana/` owns monitoring integrations, fixtures, its runner, and the notification sink; `redis/` owns the isolated Redis runner. Shared test lifecycle and stale-project helpers live directly at the test root. Runners stay with their suite, not in a separate scripts directory.

Run `npm run check:backend` from root for ESLint and typechecking, and `npm run test:backend` for all backend tests. Use `npm run test:unit -w backend` for unit tests or `npm run test:integration -w backend` for monitoring, real-Redis, and Discord integration tests. `lint:backend` and `typecheck:backend` run each static check separately. Root commands delegate to backend-owned scripts. Docker must be available for the Redis and monitoring integrations. Direct integration commands use `npm run test:integration:monitoring -w backend`, `:discord`, or `:redis`.

The Redis runner starts a disposable Compose project with its own backend test image and Redis service. It reuses the repository Redis TLS configuration and mounts temporary one-day CA/server certificates generated by the runner, plus a fixed test-only password in Compose. It does not read `apps/backend/.env` or inherit the runtime service definitions. Redis must pass its health check before the tests start. Its internal network and data volume are isolated from the development stack and removed afterward, including on test failure; the runner also removes the temporary certificates. The test has a 120-second timeout; initial Redis connections use `REDIS_CONNECT_TIMEOUT_MS` (default 10000 milliseconds).

The root `npm run test` opens an interactive menu for the API environment and safe/full scope. Safe mode runs `test:ci`; full mode requires confirmation and enables the Discord webhook and 429 spike tests, which can send a message and trigger alerts. The spike config needs Grafana credentials. Mocked UI tests verify frontend behavior and API contracts, not the deployed backend. The live flow needs a reachable selected API/Auth0 tenant and dedicated test credentials. Install the required browser projects with `npx playwright install chromium firefox webkit msedge`. Google automation is explicitly skipped, and Cloudflare may require manual verification; see the shared [local testing guide](../apps/documentation/docs/general-info/testing.mdx), the [backend automated testing guide](../apps/documentation/docs/backend/local-testing/automated-testing.mdx), and the [frontend automated testing guide](../apps/documentation/docs/frontend/local-testing/automated-testing.mdx).

## Rate limiting and proxy trust

The backend uses an atomic Redis fixed-window limiter. OAuth initiation and callback, logout, self-service mutations, and admin mutations use separate route groups. Keys contain Fastify's resolved client IP, the authenticated session subject when available, and the normalized route group; query strings are never included.

Redis failures use a bounded local fallback of 10,000 active keys. This fallback is an availability policy, not a replacement for shared enforcement, and deployments should alert on Redis errors.

`TRUST_PROXY` defaults to `false`. Set it to `true` only when the ingress overwrites `X-Forwarded-For` and `X-Forwarded-Proto`; or set an explicit IP/CIDR string (or comma-separated list) matching the trusted proxy chain. Numeric hop counts are not supported — Fastify disabled that mode because it cannot validate the immediate peer and lets direct clients spoof `X-Forwarded-*` headers. Never expose Fastify directly to untrusted clients while proxy trust is enabled.
