## Commands

Run commands from the repository root. For shared root-gate requirements, the latest full-run result, and common result boundaries, see the [Local Testing guide](../../general-info/testing.mdx).

| Command                                     | Purpose                                                             |
| ------------------------------------------- | ------------------------------------------------------------------- |
| `npm run check:backend`                     | Run backend ESLint and TypeScript checks through the workspace.     |
| `npm run test:backend`                      | Run backend unit, monitoring, Redis, and Discord integration tests. |
| `npm run test:integration:redis -w backend` | Run only the isolated Redis test; Docker is required.               |

Backend-owned unit tests live in `apps/backend/src/tests/`; they cover API routes, services, sessions, security, rate limiting, and Auth0 integration/scripts. The Grafana rule and Discord webhook checks live in `apps/backend/monitoring/tests/`. Frontend feedback/localization contracts live in `apps/frontend/tests/`, Auth route and proof-resume tests live with the Auth app, and shared toast tests live in `shared/packages/ui/src/tests/`.

The Redis check starts a disposable Docker Compose project using `apps/backend/docker/compose/docker-compose.test.redis.yml`. It builds the Dockerfile's `builder` target, which retains backend test sources, and a Redis service without loading `apps/backend/.env` or extending runtime Compose services. The default production image instead removes `src/tests` and `monitoring/tests`. Its fixed test-only password is scoped to the internal Docker network. The Redis TLS configuration is shared, but the runner generates its own one-day test CA and Redis certificate in a temporary directory; it never mounts developer certificates or needs host OpenSSL. Redis must pass an authenticated TLS health check before tests start. The project uses its own network and data/log volumes, publishes no ports, and removes its containers, data volume, and temporary certificates afterward, including on failure. No running development stack is required. Redis readiness is limited to ten health-check attempts, and the test file has a 120-second timeout. `REDIS_CONNECT_TIMEOUT_MS` bounds initial session-store connections (default 10000 milliseconds).

The live Playwright suite covers Chromium, Firefox, and Edge in one invocation. Keep dedicated `TESTUSER_EMAIL` / `TESTUSER_PASSWORD` credentials for that integration suite.

## Test Boundaries

- **Backend:** `npm run check:backend` runs lint/types; `npm run test:backend` runs unit, monitoring, Redis, and Discord integration tests. The Redis suite uses a disposable real Redis service.
- **Frontend:** `npm run test:e2e:mocked` runs mocked browser/accessibility checks; `npm run build:frontend` builds both apps and docs. See [Frontend Automated Testing](../../frontend/local-testing/automated-testing.mdx).
- **Cross-system integration:** `npm run test:e2e:real` exercises the connected apps, API, and live Auth0 password flow in Chromium, Firefox, and Edge in one invocation. It is not a backend-only or frontend-only gate; Google automation is intentionally skipped.

Passing backend unit, monitoring, and Redis tests does not prove every branch, production workload, or failure mode. Monitoring test rules are derived from production definitions in a temporary file; only timing is accelerated. See the [Local Testing guide](../../general-info/testing.mdx) for shared root-gate interpretation and limits.
