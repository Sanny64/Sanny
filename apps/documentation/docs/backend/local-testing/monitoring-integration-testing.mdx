The monitoring-rule suite uses a disposable Compose project and a local notification test sink. It does not send external email or Discord notifications and does not load `apps/backend/.env`. The separate direct Discord webhook test sends a real message, so run it only when that side effect is intended.

## Prerequisites

- Ensure `DISCORD_WEBHOOK` is already available in the environment before running the direct webhook test. The test menu sets it from `DEV_DISCORD_WEBHOOK` for full development runs only; `PROD_DISCORD_WEBHOOK` is never used by tests. With `RUN_DISCORD_INTEGRATION=true`, the monitoring suite also verifies that the notification policy routes warning and critical alerts to `discord-alerts` (the local policy has no email route) and asks Grafana to send a test notification through that contact point. With `RUN_EMAIL_INTEGRATION=true` it additionally sends one test email through `email-alerts`. Both run only against loopback API hosts.
- In Grafana, verify alert rules are loaded under **Alerting > Alert rules**.
- Before triggering a rule, wait for existing 429/auth-volume/callback-flood alerts to resolve.

The Grafana image is a minimal runtime image without npm. Use the workspace commands below; the monitoring runner manages its own disposable stack.

## Email Contact Point

Use Grafana's built-in contact-point test. The development stack never routes alerts to email, so this is the only way local runs send mail. The full development test run does it once through `RUN_EMAIL_INTEGRATION=true` (`email-delivery.spec.ts`, loopback hosts only) and sends one real email to the addresses in `contactpoints.yml`. Manual steps:

1. Open Grafana through the authenticated `/grafana/` path.
2. Open **Alerting → Notification configuration → Contact points**.
3. Edit `email-alerts`, choose **Test**, and send the built-in test notification.
4. Confirm receipt in the configured mailbox.

Delivery and Grafana notification history are the evidence; configuration alone does not prove delivery.

## Direct Discord Webhook

Run the opt-in webhook test locally from the repository root. It uses the backend workspace source and does not require a running development stack:

```powershell
$env:RUN_DISCORD_INTEGRATION = "true"
npm run test:integration:discord -w backend
```

The test sends a synthetic message through the webhook provided in the test process environment and expects HTTP `204`. It checks the webhook itself, not Grafana alert routing. Run it only when a visible test message in that Discord destination is acceptable.

---

## Trigger Grafana Rules

Run the isolated monitoring integration from the repository root:

```powershell
npm run test:integration:monitoring -w backend
```

The runner builds a disposable Grafana/Loki stack, sends bounded synthetic entries above the three log-rule thresholds, and verifies that `429 Rate Limit Spike`, `Auth Endpoint Abuse`, and `Auth Callback Flood` fire and reach the test sink. It accelerates only rule timing, then removes the test stack and temporary rules. It does not use production credentials or deliver external notifications.

Synthetic Loki entries use `source="integration-test"` and are removed with the disposable test stack.

## Real NGINX 429 Scenario

The separate Playwright scenario authenticates to Grafana through protected NGINX, confirms that `429 Rate Limit Spike` is not already firing, sends 40 requests through local NGINX to `/api/v001/auth`, and expects more than 20 HTTP `429` responses. It then polls Grafana for up to four minutes until that rule is firing. This verifies the rule state, not external notification delivery.

In PowerShell at the repository root:

```powershell
$env:RUN_429_SPIKE_E2E = "true"
node tooling/scripts/test/run-suites.mjs --monitoring-only
```

This Chromium test uses `shared/tests/e2e/playwright.monitoring.config.ts` and is invoked by regular E2E and full test runs, but skips unless `RUN_429_SPIKE_E2E=true`. Set that variable only when the alert side effect is intended; the test also needs Grafana credentials to verify the firing alert.
