:::warning[Warnung vor flackernden visuellen Inhalten]
Live-E2E-Tests öffnen sichtbare Browserfenster (`--headed`) und können flackernde oder schnell wechselnde visuelle Inhalte anzeigen. Personen mit photosensibler Epilepsie oder Empfindlichkeit gegenüber Lichtblitzen sollten während der Tests nicht auf die Browserfenster schauen.
:::

## Befehle

Alle Befehle im Repository-Stammverzeichnis ausführen. Laufzeitversionen und gemeinsame Root-Gate-Voraussetzungen stehen im [Leitfaden zu lokalen Tests](../../general-info/testing.mdx). Installiere Chromium, Firefox, WebKit und Edge mit `npx playwright install chromium firefox webkit msedge`. Gemockte Accessibility- und Routing-Smoke-Tests sind in `npm run test:e2e:mocked` enthalten und laufen zusätzlich auf WebKit; Live-Auth0 verwendet weiterhin Chromium, Firefox und Edge. Linux verwendet eigene neun Chromium-Screenshot-Baselines statt der Windows-Bilder. `npm run test:visual:linux` vergleicht sie im offiziellen, an die Lockfile angepassten Playwright-Container; `npm run test:visual:linux -- --update` erzeugt sie zur Prüfung neu. Sowohl PR-`test:ci` als auch das vollständige lokale `npm run test` enthalten diese Prüfung. Docker ist erforderlich; in den temporären Arbeitsbereich werden nur geheimefreie Quelldateien kopiert. Der erste Lauf baut ein lokales Docker-Image namens `sanny64-visual-deps` mit npm und Linux-Abhängigkeiten. Weitere Läufe verwenden es ohne Neuinstallation. Änderungen an kopierten Paketmanifesten, der Lockfile (einschließlich Playwright-Version) oder `tooling/scripts/Dockerfile.visual` wählen automatisch ein neues Image. Jeder Lauf kopiert aktuelle Quelldateien in einen kurzlebigen Container; normale Vergleiche binden den temporären Quellordner schreibgeschützt ein. Nur `--update` schreibt Linux-Snapshots zurück. Der Build-Kontext enthält ausschließlich Paketmanifeste, Lockfile und Dockerfile, keine Anwendungsquellen oder Umgebungsdateien. Der Cache gilt nur für den lokalen Docker-Daemon; neue CI-Runner benötigen weiterhin den ersten Build. `docker image ls sanny64-visual-deps` zeigt die Images; ungenutzte Versionen lassen sich mit `docker image rm <image-id>` entfernen. Fehlende Images werden beim nächsten Lauf neu gebaut.

| Befehl                                                                  | Zweck                                                                                                              |
| ----------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| `npm run test:e2e:mocked`                                               | Mock-Suite in Chromium, Firefox und Edge; ausgewählte Accessibility- und Sanny-Routing-Tests zusätzlich in WebKit. |
| `npm run test:visual:linux`                                             | Linux-Chromium-Visual-Baselines in Docker vergleichen.                                                             |
| `npx playwright test shared/tests/e2e/mock/auth-accessibility.spec.ts`  | Nur Auth-Accessibility-Tests ausführen.                                                                            |
| `npx playwright test shared/tests/e2e/mock/sanny-accessibility.spec.ts` | Nur Sanny-Accessibility-Tests ausführen.                                                                           |
| `npx playwright test shared/tests/e2e/mock/accessibility.spec.ts`       | Nur gemeinsame Accessibility-Tests ausführen.                                                                      |
| `npm run test:e2e:real`                                                 | Live-Auth0-Tests in Chromium, Firefox und Edge in einem Playwright-Aufruf.                                         |
| `npm run test:components`                                               | Vitest-Komponententests für das gemeinsame UI-Paket.                                                               |
| `npm run check -w auth`                                                 | Auth-Lint und Typprüfung über die Workspace-Basisskripte ausführen.                                                |
| `npm run check -w sanny`                                                | Sanny-Lint und Typprüfung über die Workspace-Basisskripte ausführen.                                               |
| `npm run lint:auth`                                                     | Auth-Frontend linten.                                                                                              |
| `npm run lint:sanny`                                                    | Öffentliches Frontend linten.                                                                                      |
| `npm run lint -w @sanny/i18n`                                           | Gemeinsames Lokalisierungspaket linten.                                                                            |
| `npm run lint -w @sanny/styles`                                         | Gemeinsames Styles-Paket linten.                                                                                   |
| `npm run lint -w @sanny/ui`                                             | Gemeinsames UI-Paket linten.                                                                                       |
| `npm run build:auth`                                                    | Auth bauen; statische Prüfungen vorher separat ausführen.                                                          |
| `npm run build:sanny`                                                   | Sanny bauen; statische Prüfungen vorher separat ausführen.                                                         |

Das Workspace-`check`-Skript jeder App setzt sich aus den Basisskripten `lint` und `typecheck` zusammen; keine der Apps bietet einen Test-Alias für Lint. Die gemockte Browser-Suite enthält die Accessibility-Specs; die direkten Playwright-Befehle oben sind nützlich, wenn an einer einzelnen Suite gearbeitet wird. Gemeinsames Test-Gate-Verhalten und Ergebnisgrenzen stehen im [Leitfaden zu lokalen Tests](../../general-info/testing.mdx). Backend-Testabdeckung steht unter [Automatisierte Backend-Tests](../../backend/local-testing/automated-testing.mdx).

## Komponentenabdeckung

`shared/packages/ui/src/tests/component/ui-components.test.tsx` prüft Tastaturbedienung und Deaktivierung von Buttons, Checkbox-Beschriftungen und Feedback, Toast-Status-/Fehlermeldungen und Aktionen, Theme-/Sprachpersistenz sowie Fehlerseiteninhalt. Nicht jede Prop- oder Zustandskombination ist abgedeckt.

## Browserabdeckung

Die Standard-Playwright-Konfiguration wählt nur gemockte Tests aus. Direkte Live-Aufrufe benötigen `--config=shared/tests/e2e/playwright.real.config.ts`; die vorhandenen Live-npm-Skripte enthalten diese Option bereits. CI lehnt fokussierte Tests ab und kann keine laufenden Entwicklungsserver wiederverwenden. Bei gemockten Fehlschlägen bleiben Traces/Screenshots erhalten; Artefakte für Live-Authentifizierung bleiben deaktiviert. Siehe [Tooling](../../general-info/tooling).

Gemockte Playwright-Tests liegen in `shared/tests/e2e/mock/`. Die Accessibility-Tests sind auf `auth-accessibility.spec.ts` und `sanny-accessibility.spec.ts` verteilt und mit den app-spezifischen Befehlen oben einzeln ausführbar. Weitere Specs prüfen Routen/Lokalisierung, Login/Logout, Settings/Admin und Account-Linking. Öffentliche Inhaltsseiten zeigen derzeit übersetzte Platzhalter ohne interaktive Steuerelemente; die eigenständigen Spiele Guess-the-Number und Blockrunner sind von den Interaktionstests dieses Projekts ausgenommen. Gemockte API-Antworten belegen nur Frontend-Verhalten und API-Verträge, nicht Backend-Persistenz oder Live-Auth0-Verhalten.

Axe prüft mit WCAG-2.2-AA-Tags alle registrierten öffentlichen Sanny-Routen und die getesteten Settings-/Admin-Zustände sowie die Auth-Hilfsrouten. Die app-eigenen Accessibility-Specs decken englische/deutsche Spracheinstellungen und helle/dunkle Themes in Chromium, Firefox und Edge ab. `accessibility.spec.ts` prüft zusätzlich die Initialisierung von Sprache und Theme in beiden Apps sowie System-Theme-Wechsel mit gespeicherter manueller Auswahl in den Sanny-Settings. Diese automatisierten Prüfungen ersetzen weder Screenreader-Prüfungen noch Tests bei 200% Zoom.

## Aussagekraft eines erfolgreichen Testlaufs

- Frontend-Lint/Build prüft den aktuellen App- und Shared-Package-Quellcode mit den konfigurierten Werkzeugen. Komponenten- und gemockte Browsertests prüfen die erfassten UI-Zustände sowie Request-/Response-Verträge in den konfigurierten Browsern.
- Axe prüft automatisierte WCAG-2.2-AA-Regeln nur für die in der Suite enthaltenen Routen, Zustände, Sprachen und Themes. Bestimmte Tastaturabläufe sind abgedeckt, jedoch kein vollständiges Tastatur-Audit.

Axe- und Browsertests sind auf geprüfte Regeln und UI-Zustände begrenzt; sie belegen weder vollständige WCAG-Konformität noch Screenreader-Kompatibilität. Visuelle Baselines werden nur in Chromium erstellt. Gemeinsame Grenzen von Testergebnissen und Hinweise zu Nachweisen stehen im [Leitfaden zu lokalen Tests](../../general-info/testing.mdx).
