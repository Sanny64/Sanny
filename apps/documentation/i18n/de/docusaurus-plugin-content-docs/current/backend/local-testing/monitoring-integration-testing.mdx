# Monitoring-Integrationstests

Die Suite für Monitoring-Regeln verwendet ein wegwerfbares Compose-Projekt und einen lokalen Benachrichtigungs-Test-Sink. Sie versendet keine externen E-Mails oder Discord-Nachrichten und lädt `apps/backend/.env` nicht. Der separate direkte Discord-Webhooktest versendet eine echte Nachricht; führe ihn nur aus, wenn dieser Nebeneffekt beabsichtigt ist.

## Voraussetzungen

- Vor dem direkten Webhooktest sicherstellen, dass `DISCORD_WEBHOOK` bereits in der Umgebung gesetzt ist.
- In Grafana prüfen, ob die Alarmregeln unter **Alerting > Alert rules** geladen sind.
- Vor einem Trigger-Test warten, bis vorhandene 429-, Auth-Volumen- oder Callback-Flood-Alarme beendet sind.

Das Grafana-Image ist ein minimales Laufzeit-Image ohne npm. Verwende die Workspace-Befehle unten; der Monitoring-Runner verwaltet seinen eigenen wegwerfbaren Stack.

---

## E-Mail-Kontaktpunkt testen

Grafanas integrierten Kontaktpunkttest verwenden:

1. Grafana über den authentifizierten Pfad `/grafana/` öffnen.
2. **Alerting → Notification configuration → Contact points** aufrufen.
3. Den Kontaktpunkt `email-alerts` bearbeiten und **Test** auswählen.
4. Die vordefinierte Testbenachrichtigung senden und den Eingang im konfigurierten Postfach bestätigen.

Dabei wird eine echte E-Mail versendet. Zustellung und Benachrichtigungshistorie in Grafana sind der Nachweis; eine SMTP-Konfiguration allein beweist keine erfolgreiche Zustellung.

## Direkter Discord-Webhook

Den explizit aktivierten Webhooktest lokal im Repository-Stammverzeichnis ausführen. Er nutzt den Backend-Workspace und benötigt keinen laufenden Entwicklungs-Stack:

```powershell
$env:RUN_DISCORD_INTEGRATION = "true"
npm run test:integration:discord -w backend
```

Der Test versendet eine synthetische Nachricht über den Webhook aus der Umgebung des Testprozesses und erwartet HTTP `204`. Er prüft den Webhook selbst, nicht Grafanas Alarmweiterleitung. Nur ausführen, wenn eine sichtbare Testnachricht im konfigurierten Discord-Ziel in Ordnung ist.

---

## Grafana-Regeln auslösen

Die isolierte Monitoring-Integration im Repository-Stammverzeichnis ausführen:

```powershell
npm run test:integration:monitoring -w backend
```

Der Runner erstellt einen wegwerfbaren Grafana-/Loki-Stack, sendet begrenzte synthetische Einträge oberhalb der Schwellenwerte der drei Logregeln und prüft, ob `429 Rate Limit Spike`, `Auth Endpoint Abuse` und `Auth Callback Flood` ausgelöst und an den Test-Sink zugestellt wurden. Nur das Regel-Timing wird beschleunigt; anschließend entfernt der Runner Test-Stack und temporäre Regeln. Produktionszugangsdaten oder externe Benachrichtigungen werden nicht verwendet.

Die synthetischen Loki-Einträge verwenden `source="integration-test"` und werden mit dem wegwerfbaren Test-Stack entfernt.

## Echten NGINX-429-Anstieg testen

Dieses separate Playwright-Szenario authentifiziert sich bei Grafana hinter dem geschützten NGINX, bestätigt, dass `429 Rate Limit Spike` noch nicht aktiv ist, sendet 40 Requests über den lokalen NGINX-Proxy an `/api/v001/auth` und erwartet mehr als 20 HTTP-`429`-Antworten. Anschließend fragt es Grafana bis zu vier Minuten lang ab, bis die Regel aktiv ist. Dies prüft den Regelstatus, nicht die externe Zustellung von Benachrichtigungen.

In PowerShell im Repository-Stammverzeichnis:

```powershell
$env:RUN_429_SPIKE_E2E = "true"
npm run test:e2e:429
```

Der Test verwendet `shared/tests/e2e/playwright.monitoring.config.ts` und nur Chromium. Er wird von normalen E2E- und vollständigen Testläufen aufgerufen, aber übersprungen, sofern `RUN_429_SPIKE_E2E=true` nicht gesetzt ist. Setze die Variable nur, wenn der Alarm-Nebeneffekt beabsichtigt ist; zur Prüfung des ausgelösten Alarms benötigt der Test außerdem Grafana-Zugangsdaten.
