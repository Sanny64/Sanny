Dieses Projekt verwendet einen einfachen Release-Zug für ein Monorepo mit:

- Frontend `sanny`.
- Frontend `auth`.
- Docusaurus-Dokumentationsseite `documentation`.
- Fastify-Backend.
- Gemeinsam genutzte Pakete unter `shared/packages/**`.
- Gemeinsam genutzte Tests unter `shared/tests/**`.

Ziel ist es, `main` sehr übersichtlich zu halten (ein Commit pro Release), eine echte Web-Testumgebung zu unterstützen und den Ablauf für eine einzelne entwickelnde Person einfach ausführbar zu machen.

## Branch-Modell

Dieses Projekt verwendet `dev -> test -> main`.

Dies ist die dokumentierte Release-Konvention des Repositorys, keine von GitHub Actions erzwungene Branch-Protection-Regel. Der Push-Einstiegspunkt des Release-Workflows ist auf `main` und `test` begrenzt; sein Planner wählt Deployment-Ziele anhand geänderter Pfade. GitHub Actions erzwingen weder Pull-Requests noch Merge-Richtlinien.

### `dev`

- Täglicher Entwicklungs-Branch.
- Feature-Arbeit landet zuerst hier.
- Die Commit-Historie kann unaufgeräumt sein und wird niemals umgeschrieben.
- Von `dev` wird keine Website deployed, und nichts darin gilt als releasebereit, bevor es nach `test` übernommen wurde.
- Pushes nach `dev` lösen keinen Deployment-Workflow aus.

### `test`

- Branch für Release-Kandidaten.
- Stellt die internet-erreichbare, durch Basic Auth geschützte Testumgebung bereit.
- Dient dazu, das konkrete Release vor der Produktion im Web zu prüfen.
- Fehlerbehebungen für den Release-Kandidaten landen zuerst hier.
- Die vollständige Commit-Historie bleibt erhalten und wird niemals umgeschrieben.

### `main`

- Ausschließlich für Produktion.
- Wird sauber und übersichtlich gehalten: genau ein Commit pro Release.
- Wird niemals gemergt. Jeder Release-Commit wird aus dem Dateibaum von `test` erstellt (siehe [„`test` nach `main` übernehmen“](#5-test-nach-main-übernehmen)).
- Jeder Release-Commit erhält einen Tag im Format `release-1.0.0.x`.
- `main` und `test` teilen absichtlich keine Commit-Historie. Zum Release-Zeitpunkt haben sie lediglich identische Datei-Inhalte.

## Zuordnung der Deployments

Der Workflow **Release workspace** (`.github/workflows/release.yml`) ist der einzige Push-/manuelle Einstiegspunkt für Releases auf `main` und `test`. Sein geheimnisfreier Planner wählt die Ziele anhand geänderter Pfade und ruft vor wiederverwendbaren Deployment-Workflows einmalig `verify.yml` auf. Pull Requests rufen die Verifikation weiterhin separat auf. App-spezifische Änderungen wählen die jeweilige App, Backend-Änderungen das Image, und Änderungen an Shared-/Tooling-/Workflow-Pfaden wählen konservativ alle Produktionsziele. GitHub-Branch-Protection muss die Verifikation separat voraussetzen. Actions bleiben per SHA gepinnt, und FTPS prüft vertrauenswürdige Zertifikate mit passendem Hostnamen.

**Migration für Betreiber:** Die Workflows `deploy-*.yml` stellen nur noch `workflow_call` bereit. Verwende für manuelle Starts **Release workspace**. Ein manueller Lauf auf `main` baut alle Produktionsziele neu; aktiviere **deploy-backend** nur, wenn das VPS-Deployment beabsichtigt ist. Ein manueller Lauf auf `test` deployed unabhängig von dieser Eingabe nur die Testseiten. Andere Branches werden übersprungen. Jeder Unterworkflow erhält nur die von ihm benötigten Secrets, die Verifikation erhält keine. Die CI verwendet `tooling/config/.nvmrc` und npm 11.6.3.

Die Repository-Variablen `VITE_DEV_API_URL` und `VITE_PROD_API_URL` müssen die jeweils erreichbaren HTTPS-API-Origins enthalten. Test- und Produktionsworkflows übergeben den ausgewählten Wert als `VITE_API_URL`; Browser-Code verwendet nur diesen kanonischen Wert. Lokal kann Vite im Entwicklungs-/Testmodus weiterhin den Entwicklungswert und im Produktionsmodus den Produktionswert verwenden; ein explizites `VITE_API_URL` hat Vorrang. Builds lehnen fehlende oder ungültige Origins ab.

### Testumgebung

Ein Push nach `test` stellt die im Internet erreichbare Testumgebung mit HTTP Basic Auth für Website-Besucher bereit.

- `sanny` -> `/public_html/testing/`, erreichbar unter `https://test.sanny64.de/`.
- `auth` -> `/public_html/testing/apps/frontend/auth/`, erreichbar unter `https://test.auth.sanny64.de/`.
- `docs` -> `/public_html/testing/docs/`, erreichbar unter `https://test.docs.sanny64.de/`, mit der deutschen Website unter `/de/`.
- Der Koordinator ruft `.github/workflows/deploy-to-test.yml` auf. Dieser Workflow baut die drei Websites und lädt sie mit jeweils eigener FTP-Synchronisationsdatei und den vorhandenen FTP-Secrets hoch. Manuelle Test-Releases laufen über **Release workspace** auf `test`.
- Die verschachtelten Verzeichnisse sind Dokumentenwurzeln beim Hoster, keine URL-Präfixe; alle Builds verwenden `/`. Subdomains und HTTPS müssen bei Hetzner eingerichtet werden. Der Workflow verwendet feste FTP-Ziele: `/public_html/testing/`, `/public_html/testing/apps/frontend/auth/` und `/public_html/testing/docs/`.
- `TEST_BASIC_AUTH_ENTRY` enthält eine oder mehrere durch Zeilenumbrüche getrennte Zeilen im Format `username:hashed-password`. Jede Zeile legt einen eigenen Zugang an; alle Zugänge funktionieren auf allen drei Websites. Leerzeilen sind nicht erlaubt. Der Workflow erzeugt `.htpasswd` aus diesem Secret und lädt die Datei zusammen mit der Sanny-Website per FTP hoch. `TEST_BASIC_AUTH_FILE_PATH` enthält den absoluten Server-Dateisystempfad zur Datei `/public_html/testing/.htpasswd`, nicht den FTP-sichtbaren Pfad. Alle drei Websites müssen diese gemeinsame Passwortdatei lesen dürfen.
- Test-Builds setzen Asset- und Router-Basispfade, ohne die Produktions-Defaults zu ändern. Apache-Rewrite-Regeln unterstützen das Neuladen verschachtelter React-Routen.

#### Basic-Auth-Zugang erzeugen

Erzeuge mit Docker einen bcrypt-Passwort-Hash:

```powershell
docker run --rm -it httpd:2.4-alpine htpasswd -nB tester
```

Ersetze `tester` durch den gewünschten Benutzernamen und gib das Passwort ein, wenn du dazu aufgefordert wirst. `htpasswd` gibt die vollständige Zeile im Format `benutzername:hash` aus. Füge diese Zeile zu `TEST_BASIC_AUTH_ENTRY` hinzu. Für jeden Zugang kommt eine Zeile ohne Leerzeilen hinzu.

Der Workflow erstellt `.htpasswd` bei jedem Deployment neu aus `TEST_BASIC_AUTH_ENTRY`; vorhandene Einträge werden nicht angehängt. Kopiere daher vor dem Hinzufügen eines Zugangs alle bestehenden `benutzername:hash`-Zeilen aus der aktuellen `.htpasswd`-Datei in `TEST_BASIC_AUTH_ENTRY` und ergänze anschließend die neue Zeile. Andernfalls funktionieren die bisherigen Zugänge nicht mehr.

- Quellcodeexportierte gemeinsame Pakete werden in die betroffenen Frontend-Builds eingebunden; sie erzeugen keine eigenständige Build-Ausgabe.
- Der Test-Workflow stellt nur die Frontend-Apps und die Dokumentation bereit, nicht das Backend.

Das lokale Artefakt enthält `testing-site/sanny`, `testing-site/auth` und `testing-site/docs`. Diese Staging-Verzeichnisse entsprechen der Upload-Matrix; die Workspace-Quellpfade ändern ihre Namen nicht. Repository-Verträge führen den Staging-Schritt mit synthetischen Builds und Basic-Auth-Einträgen in einem temporären Verzeichnis aus.

### Produktion

Auf `main` wählen App-Pfade Auth oder Sanny, Dokumentationspfade die Docs und Backend-Pfade das Backend-Image. Änderungen an Shared Packages oder gemeinsamen Tooling-/Workflow-Pfaden wählen vorsorglich alle Produktionsziele. Ein manueller **Release workspace**-Lauf auf `main` wählt ebenfalls alle Ziele.

- `sanny` -> Produktionsseite unter `https://sanny64.de/`.
- `auth` -> Produktionsseite unter `https://auth.sanny64.de/`.
- `docs` -> Produktionsseite unter `https://docs.sanny64.de/`, mit der deutschen Website unter `/de/`.
- Quellcodeexportierte Shared Packages werden in die betroffenen App-Builds gebündelt; sie haben keinen eigenständigen Build-Output.
- Ein Push nach `main`, der das Backend-Ziel auswählt, führt die gemeinsame Verifikation aus und veröffentlicht dieselben `latest`- und Commit-SHA-Tags nach GHCR und Docker Hub (`sanny64/backend`). Backend-, Shared-/Tooling- und Workflow-Änderungen können dieses Ziel auswählen. Docker Hub bleibt die Image-Quelle für Gordons Analyse und das VPS-Deployment.
- Ein manueller **Release workspace**-Lauf auf `main` mit aktiviertem **deploy-backend** veröffentlicht und deployed genau diesen Commit-SHA-Tag von Docker Hub. Ohne diese Eingabe wird das Image veröffentlicht, der VPS bleibt unverändert. Docker-Hub-Zugangsdaten sind GitHub-Actions-Secrets, keine Backend-Laufzeitvariablen.

Backend-Tags verwenden den vollständigen unveränderten Commit-SHA, keine Kurzform mit Präfix. Gib im manuellen Release `backend-directory` an; die Eingabe wird als `BACKEND_DEPLOY_DIRECTORY` übergeben und muss auf einen vom Betreiber bereitgestellten VPS-Checkout dieses Commits mit unveränderter versionierter Deployment-Konfiguration und separat bereitgestellten Secrets/Zertifikaten zeigen. Der Workflow stoppt bei abweichendem Stand, validiert Compose ohne Konfigurationsausgabe und wartet auf den Backend-Healthcheck. Er kopiert keine Konfiguration und bietet keinen automatischen Rollback. Beachte vor der Aktivierung des VPS-Deployments [Deployment und Wiederherstellung](../backend/deployment.mdx).

## Regel für gemeinsam genutzte Pakete

Änderungen an `shared/packages/**` wirken sich immer auf Frontend-Builds aus.

Das bedeutet:

- Jede relevante Änderung in `shared/packages/**` muss die Frontend-Pipeline auslösen.
- Gemeinsam genutzte Pakete werden nicht eigenständig manuell deployed.
- Ändert sich ein gemeinsam genutztes Paket, müssen die davon abhängigen Frontends in Test- und Produktionsumgebung neu gebaut werden.

So bleibt gemeinsam genutzter Code mit den Apps synchron, die ihn verwenden.

## Release-Ablauf

### 1. Arbeit auf `dev`

- Erstelle einen Feature-Branch aus `dev`.
  - `feat/<name>`
- Nimm deine Änderungen vor.
- Führe den Feature-Branch wieder mit `dev` zusammen.

### 2. `dev` nach `test` übernehmen

- Wenn du einen Release-Kandidaten erstellen möchtest, merge `dev` nach `test`.
- Push nach `test`.
- Die Testumgebung wird automatisch deployed.

### 3. Im Web testen

- Öffne die Testumgebung in einem Browser.
- Prüfe UI, Integration, Deployment-Verhalten und alle vom Backend abhängigen Abläufe.
- Behebe Fehler, indem du von `test` aus einen Branch erstellst.

### 4. Release-Probleme auf `test` beheben

- Erstelle einen Fix-Branch aus `test`.
  - `fix/<name>`
- Nimm die Fehlerbehebung vor.
- Merge den Fix zurück nach `test`.
- Push erneut nach `test`, um die Testumgebung neu zu deployen.
- Sobald alle Fixes geprüft sind, merge `test` zurück nach `dev`, damit beide Branches wieder denselben Stand haben.

### 5. `test` nach `main` übernehmen

- Sobald die Testumgebung freigegeben und `test` zurück nach `dev` gemerged wurde, erstelle den Release-Commit auf `main`.
- Der Commit wird mit `git commit-tree` aus dem Dateibaum von `test` erstellt. Das ist kein Merge: Es können keine Merge-Konflikte entstehen, und keine Commits aus `test` landen in `main`.
- Der Commit erhält den Tag `release-1.0.0.x` und wird zusammen mit `main` gepusht.

### 6. Produktionsdeployment

- Nach dem Push des Release-Commits wird die Produktion von `main` aus deployed.
- Frontends und Docs werden automatisch deployed.
- Das Backend-Deployment erfordert einen manuellen **Release workspace**-Lauf auf `main` mit aktiviertem **deploy-backend**.

## Schritt-für-Schritt-Git-Anleitung

### An einem Feature arbeiten

Erstelle einen Feature-Branch auf Basis des Dev-Branches:

```bash
git checkout dev
git pull origin dev
git checkout -b feat/<name>
```

Committe deine Arbeit und pushe den Branch:

```bash
git add .
git commit -m "Änderung beschreiben"
git push -u origin feat/<name>
```

Wenn du fertig bist, merge den Branch zurück nach `dev`:

```bash
git checkout dev
git pull origin dev
git merge feat/<name>
git push origin dev
```

### Einen Release-Kandidaten starten

Wenn `dev` releasebereit ist:

```bash
git checkout test
git pull origin test
git merge dev
git push origin test
```

Dadurch wird die Testumgebung deployed.

### Das Release testen

Prüfe auf der öffentlichen Testseite:

- Layout und UI.
- Routing.
- API-Verhalten.
- Änderungen an gemeinsam genutzten Paketen.
- Deployment-spezifische Probleme.

Wenn alles funktioniert, fahre mit der Produktion fort. Andernfalls behebe den Fehler auf `test`.

### Ein auf `test` gefundenes Problem beheben

Erstelle einen Bugfix-Branch auf Basis von `test`:

```bash
git checkout test
git pull origin test
git checkout -b fix/<name>
```

Nimm die Fehlerbehebung vor und merge sie anschließend zurück nach `test`:

```bash
git add .
git commit -m "Release-Problem beheben"
git checkout test
git pull origin test
git merge fix/<name>
git push origin test
```

Wiederhole dies für alle Fehler. Nachdem jeder Fix auf `test` geprüft wurde und das Release vollständig stabil ist, merge `test` nach `dev`:

```bash
git checkout dev
git pull origin dev
git merge test
git push origin dev
```

### Für die Produktion freigeben

Wenn `test` freigegeben und zurück nach `dev` gemerged ist, erstelle den Release-Commit auf `main`.

Ersetze `1.0.0.x` in allen drei Stellen durch die neue Version (Bash / Git Bash):

```bash
git fetch origin
git checkout main
git merge --ff-only origin/main
NEW=$(git commit-tree 'origin/test^{tree}' -p origin/main -m "Release 1.0.0.x")
git merge --ff-only "$NEW"
git tag release-1.0.0.x
git push origin main release-1.0.0.x
```

PowerShell-Variante:

```powershell
git fetch origin
git checkout main
git merge --ff-only origin/main
$NEW = git commit-tree "origin/test^{tree}" -p origin/main -m "Release 1.0.0.x"
git merge --ff-only $NEW
git tag release-1.0.0.x
git push origin main release-1.0.0.x
```

Die Befehle bewirken:

- `git fetch origin` und `git merge --ff-only origin/main` bringen das lokale `main` auf den aktuellen Stand und brechen ab, wenn der Branch auseinander gelaufen ist.
- `git commit-tree 'origin/test^{tree}' -p origin/main` erstellt einen neuen Commit mit exakt den Dateien aus `test` und dem bisherigen `main`-Commit als einzigem Vorgänger. Commits aus `test` werden nicht übernommen.
- `git merge --ff-only "$NEW"` setzt `main` auf diesen Commit vor. Dabei werden keine Dateien überschrieben und kein Force-Push benötigt.
- Der Tag kennzeichnet das Release und wird zusammen mit `main` übertragen.

Prüfe anschließend das Ergebnis:

```bash
git diff --stat origin/test main
git log --oneline -3 main
```

Der erste Befehl darf nichts ausgeben, da beide Branches denselben Datei-Inhalt haben müssen. Die Log-Ausgabe zeigt einen Release-Commit pro Version.

Hinweise:

- Ist `main` auf GitHub geschützt und sind Pull Requests erforderlich, wird der direkte Push abgelehnt. Erlaube den Push für dein Administratorkonto oder deaktiviere die Regel für `main`.
- Pull Requests und CI gehören nicht zu diesem Schritt; die Prüfung erfolgt vorher auf der Testumgebung.
- Falls ein Release fehlerhaft ist, behebe den Fehler auf `test` und erstelle das nächste Release. Schreibe `main` nicht um.

#### Beispielhistorie

```text
main:  A -- R1 -- R2 -- R3                 (ein getaggter Commit pro Release)
test:  A -- a1 -- a2 -- ... -- a70 -- ...  (vollständige Historie, nie umgeschrieben)
dev:   A -- a1 -- ... -- a70 -- d1 -- ...  (vollständige Historie, nie umgeschrieben)
```

`R1`, `R2` und `R3` enthalten jeweils dieselben Dateien wie `test` zum Zeitpunkt des Releases, aber nicht dessen Commits.

#### Hotfixes

Ändere `main` niemals direkt. Jede Änderung auf `main`, die nicht in `test` enthalten ist, wird beim nächsten Release-Commit überschrieben. Hotfixes folgen dem normalen Ablauf: Fehler auf `test` beheben (Branch `fix/<name>`), nach `dev` zurückmergen und anschließend den nächsten Release-Commit erstellen.

## Feature-Branches synchronisieren

Wenn Feature-Branches auseinanderlaufen und wieder denselben Arbeitsstand verwenden sollen, nutze `dev` als Integrationspunkt.

1. Merge alle Feature-Branches lokal nach `dev` (in Abhängigkeitsreihenfolge, um Konflikte zu vermeiden).
2. Pushe `dev`.
3. Hole auf jedem Feature-Branch die Änderungen aus `dev` oder merge `dev`, um ihn zu synchronisieren.
4. Pushe die aktualisierten Feature-Branches.

Dies ist ein Wiederherstellungsschritt über den normalen Integrations-Branch `dev`. Er ist hilfreich, wenn mehrere Branches von denselben Änderungen an gemeinsam genutzten Paketen oder Workspaces abhängen und lokale Entwicklungsserver deshalb wieder konsistent laufen müssen.

## Verhalten des Produktionsdeployments

Das Produktionsdeployment startet, nachdem der Release-Commit nach `main` gepusht wurde.

- Der Planner in `release.yml` wählt Sanny-, Auth- und Dokumentations-Deployments auf `main` anhand der geänderten Pfade aus; die wiederverwendbaren Deployment-Workflows definieren keine Pfadfilter.
- Änderungen an gemeinsam genutzten Paketen lösen die Frontend-Workflows aus, die diese Pfade enthalten.
- Ein Push nach `main`, der Backend-Dateien ändert, baut und veröffentlicht dasselbe Backend-Image nach GHCR und Docker Hub; das VPS-Deployment erfordert einen manuellen **Release workspace**-Lauf auf `main` mit aktiviertem **deploy-backend**.

Damit bleibt `main` die maßgebliche Quelle für Produktion und die eigentliche Release-Historie dennoch klein.

## Hinweis zum Backend

Das Backend-Deployment ist vom Frontend-Release-Ablauf getrennt.

Das bedeutet:

- Der Test-Workflow für `test` deployed das Backend nicht.
- Ein Push nach `main`, der Backend-Dateien ändert, baut und veröffentlicht das Image nach GHCR und Docker Hub, deployed es aber nicht auf den VPS.
- Ein manueller **Release workspace**-Lauf auf `main` mit aktiviertem **deploy-backend** deployed das exakte Docker-Hub-Commit-SHA-Image und erfordert Docker-Hub- und VPS-Secrets sowie einen konfigurierten Host. `deploy-backend.yml` ist ein wiederverwendbarer Unterworkflow, kein eigenständiger manueller Workflow.
- Frontend- und Docs-Releases sollten unabhängig vom Backend-Status weiterhin dem normalen Ablauf `dev -> test -> main` folgen.
