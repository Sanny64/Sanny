## Root-Test-Gates

Führe Befehle im Repository-Stammverzeichnis mit Node.js 24 und npm 11.6.3 aus.

`npm test` im Safe-/Full-Modus und `npm run test:ci` zeigen die gesamte Testdauer mit Start-/Endzeitstempel und Exit-Ergebnis. Die gemeinsame Stopwatch in `tooling/scripts/test/stopwatch.mjs` verwendet `MM:SS` oder `H:MM:SS`; die Menüauswahl wird nicht mitgemessen. Safe verwendet die CI-Stopwatch ohne zweiten Timer.

`npm test -- --help` zeigt die Test-Einstiege, ohne Tests zu starten. Das Menü benötigt ein interaktives Terminal und weist CI-/Nicht-Terminal-Aufrufe mit einem Hinweis auf `npm run test:ci` zurück. Der CI-Wrapper setzt ausdrücklich `CI=true`, sodass fokussierte Tests und bestehende Browser-Server auch bei einer lokalen CI-Simulation abgelehnt werden. Unbekannte Argumente für Menü, CI, Suites und Visual-Runner scheitern vor der Ausführung.

- `npm run test:ci` setzt `NODE_ENV=development` und deaktiviert `RUN_CRITICAL_TESTS`, `RUN_429_SPIKE_E2E` und `RUN_DISCORD_INTEGRATION`; danach startet es `test:core` ohne Menü. Es führt Formatierungs- und statische Prüfungen, Repository-/Frontend-Verträge, Backend- und Komponententests, gemockte Browsertests, Frontend- und Dokumentations-Builds sowie Linux-Visual-Baselines aus. Docker und installierte Playwright-Browser sind erforderlich, Live-Auth0-Zugangsdaten nicht.
- `npm run test` öffnet ein interaktives Menü für Entwicklung/Produktion und den Umfang safe/full. Safe startet `test:ci`; full startet nach Bestätigung die Core-Suite, Live-Auth0, Discord und den 429-Spike. Der Live-Passwortablauf benötigt eine erreichbare ausgewählte API/einen Auth0-Tenant und dedizierte Zugangsdaten `TESTUSER_EMAIL` / `TESTUSER_PASSWORD`. Fehlende Zugangsdaten sind ein Konfigurationsfehler und kein Skip. Die Google-Automatisierung wird absichtlich übersprungen, da Google kontrollierte Browser blockieren kann; eine Auth0-Cloudflare-Challenge wird ausdrücklich zur manuellen Prüfung übersprungen.
- `npm run test:unit` führt Backend-Unit-Tests und Auth-/Sanny-/UI-Tests aus; `npm run test:contracts` führt Repository- und Frontend-Verträge aus; `npm run test:integration` startet Backend-Monitoring-/Redis-/Discord-Integrationen; `npm run test:browser` führt gemockte Browser- und Dokumentationssuiten aus. Workspaces stellen `test:unit` bereit und behalten `test` als Alias.
- Der 429-Spike wird übersprungen, sofern weder `RUN_CRITICAL_TESTS=true` noch `RUN_429_SPIKE_E2E=true` gesetzt ist; bei Aktivierung können Alarme ausgelöst werden. Full aktiviert auch `RUN_DISCORD_INTEGRATION` und sendet eine synthetische Webhook-Nachricht. Nur die aktivierte Monitoring-Konfiguration liest ersatzweise `NGINX_BASIC_AUTH_USER`, `NGINX_BASIC_AUTH_PASSWORD`, `GRAFANA_ADMIN_USER` und `GRAFANA_ADMIN_PASSWORD` aus `apps/backend/.env`; Umgebungsvariablen haben Vorrang. Das NGINX-Paar muss zu einem Eintrag in `apps/backend/nginx/secret/.htpasswd` passen; Grafana-Zugangsdaten werden gegen ein Sitzungscookie getauscht. Fehlende oder abgelehnte Zugangsdaten führen zu einer konkreten Erklärung.
- Das Menü löst Vite-Umgebungsdateien unabhängig in `apps/frontend/auth` und `apps/frontend/sanny` nach den jeweiligen `loadEnv`-Regeln auf. Es wählt ein explizites `VITE_API_URL`, andernfalls abhängig vom Ziel `VITE_DEV_API_URL` oder `VITE_PROD_API_URL`, und verlangt anschließend denselben HTTPS-Origin für beide Apps. Dieser Origin wird für den Lauf zu `VITE_API_URL` und `SANNY_E2E_API_URL`. Die backend-lokale `.env` wird nicht für Frontend-API-URLs verwendet. Ansonsten wird die API-URL in dieser Reihenfolge aufgelöst: `SANNY_E2E_API_URL`, `VITE_API_URL`, dann `https://localhost:8443`. Der Live-Browser-Server erhält diesen Origin als `VITE_API_URL`; Live-API-Aufrufe und Backend-Healthchecks verwenden denselben Origin.
- `npm run test:e2e:real`, `npm run test:e2e:429` und `npm run test:e2e` verwenden denselben Backend-Lifecycle-Manager wie `npm run test`. Er prüft `/healthcheck`, verwendet ein gesundes Backend weiter, startet Entwicklungs-Compose-Dienste nur für ein nicht erreichbares Loopback-Ziel, wartet bis zu drei Minuten und stoppt nur Dienste, die dieser Befehl gestartet hat. Ein nicht erreichbares Remote-Ziel wird niemals gestartet. Einen fehlenden Stack erstellt `npm run initialize:stack`.
- Docker-Test-Stacks (`sanny-monitoring-tests-<pid>` und `sanny-redis-tests-<pid>`) werden entfernt, wenn ihr Runner endet oder unterbrochen wird. Stacks eines hart beendeten Runners werden beim nächsten Start dieses Runners entfernt.

Beide isolierten Integrationsrunner verwenden `apps/backend/src/tests/compose-integration.mjs` für feste Pfade, Ausgabe mit Zeitstempel, Signalbehandlung und bedingungslosen Teardown. Das automatische Laden von Compose-Umgebungsdateien wird mit `COMPOSE_DISABLE_ENV_FILE=true` deaktiviert. Temporäre Monitoring-Regeln und Redis-Zertifikate werden auch bei Fehlern in Vorbereitung oder Ausführung entfernt. Redis ist eine normale isolierte Integration, kein kritisches Opt-in.

Der Full-Modus in `npm run test` aktiviert den Spike nach einer Bestätigung; `RUN_429_SPIKE_E2E=true` muss nur für den direkten Aufruf von `npm run test:e2e:429` manuell gesetzt werden:

```powershell
$env:RUN_429_SPIKE_E2E = "true"
npm run test:e2e:429
```

## Testebenen

| Ebene                                 | Root-Einstiegspunkte                                                                                                                   | Voraussetzungen und Grenzen                                                                                                                                                                                                                                                                                   |
| ------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Unit-, Komponenten- und Quellverträge | `test:auth`, `test:sanny`, `test:components`, `test:frontend:contracts`, `test:tooling`; Backend-Unit-Tests laufen über `test:backend` | Keine Live-API, kein Auth0 und keine Entwicklerzugangsdaten. Die Backend-Integrationsteile von `test:backend` benötigen zusätzlich Docker.                                                                                                                                                                    |
| Isolierte Backend-Integration         | `test:backend` oder dessen Monitoring-, Redis- und Discord-Workspace-Skripte                                                           | Monitoring und Redis verwenden temporäre Docker-Ressourcen. Redis-Tests laden keine Entwickler-Umgebungsdatei und benötigen keinen laufenden Entwicklungs-Stack.                                                                                                                                              |
| Gemockter Browser                     | `test:e2e:mocked`                                                                                                                      | Installierte Playwright-Browser und lokale Frontend-Server; API-Antworten sind gemockt, kein Live-Backend oder Auth0-Zugang erforderlich.                                                                                                                                                                     |
| Dokumentations-Browser                | `test:e2e:docs`                                                                                                                        | Baut und startet die Dokumentation lokal und testet danach mobiles Chromium; kein Backend oder Auth0 erforderlich.                                                                                                                                                                                            |
| Live-Browser                          | `test:e2e:real`                                                                                                                        | Chromium, Firefox, Edge, Netzwerkzugriff, erreichbare ausgewählte API/Auth0 und dedizierte Passwort-Testzugangsdaten. Nur diese ausdrücklich ausgewählte Konfiguration liest `TESTUSER_EMAIL` und `TESTUSER_PASSWORD` ersatzweise aus `apps/backend/.env`; andere Backend-Einstellungen werden nicht geladen. |
| Live-Monitoring                       | `test:e2e:429`                                                                                                                         | Nur nach Opt-in; das Full-Menü verlangt eine Bestätigung, Grafana-Zugangsdaten und absichtlichen Alarmverkehr. Alarme können ausgelöst werden.                                                                                                                                                                |

Tests laden Entwickler-`.env`-Dateien nicht global. Nur die ausdrücklich ausgewählten Live-Auth0- und aktivierten Monitoring-Konfigurationen laden ihre benannten Zugangsdaten-Fallbacks; CI führt `test:ci` aus und lädt keine Live-Auth0-Zugangsdaten. Vitest verwendet gemeinsame jsdom-Standards; nur die Shared-UI-Suite lädt für Cleanup eine eigene Setup-Datei. Die Browser-Konfigurationen bleiben nach Testebene getrennt, weil gemockte Apps, Live-Auth0, Monitoring und Dokumentation unterschiedliche Server und Isolationsgrenzen haben.

Deployment-Verträge benötigen die Docker-Compose-CLI und Bash; unter Windows verwenden sie Git Bash. Sie führen Staging und ein simuliertes Remote-Deployment in temporären Verzeichnissen aus und lösen Produktions-Compose mit synthetischen Eingaben auf, ohne einen VPS zu kontaktieren oder echte Umgebungsdateien zu lesen. Diese Prüfungen laufen über `test:tooling` und benötigen keinen laufenden Docker-Daemon.

`test:tooling` erkennt `shared/tests/contracts/**/*.test.mjs` automatisch; neue Verträge benötigen keine Registrierung im Package-Skript. CLI-Verträge simulieren Safe-/Full-Menüauswahl, Produktionsbestätigung, Abbruch, API-Mapping, Kindprozessfehler und Compose-Teardown ohne Live-Zugangsdaten. Diese Simulationen ersetzen nicht die manuellen Safe-/Full-Abnahmeläufe.

### 22.10.2026, Node 24/npm 11.6.3

- `npm run test:ci` war im vollständigen Gate erfolgreich. Dazu gehörten statische Prüfungen, Backend-/Frontend-Tests, 798 gemockte Browser-Erfolge (15 Skips), 2 Dokumentations-Browsertests und 5 Linux-Visualtests. - Die Ursache war eine falsche Auth0-Token-URL: Der Quellcode verwendete `/oapps/frontend/auth/token`, das mit HTTP 404 antwortete. Backend-Aufrufe und bereitgestellte Auth0 Actions verwenden nun den dokumentierten Endpunkt `/oauth/token`. Der direkte Aufruf `npm run test:e2e:real` bestand ebenfalls in Chromium und Firefox mit denselben erwarteten Anbieter-Skips.
- Der vollständige Lauf verwendete ein bereits gesundes lokales Backend weiter. Deterministische Verträge decken erfolgreiche Bereitschaft, Timeout und Abbruch ab; ein Abbruch während eines Live-Laufs wurde nicht erzwungen.

## Aussagekraft der Ergebnisse

Ein erfolgreiches Gate belegt, dass seine konfigurierten Prüfungen für den aktuellen Checkout und die lokale Testumgebung bestanden wurden. Gemockte Frontend-Tests prüfen UI-Verhalten und Request-/Response-Verträge, nicht Backend-Persistenz oder Live-Auth0. Die Live-Authentifizierung deckt nur die konfigurierte Testidentität und ausgewählte Abläufe ab. Kein lokales Gate belegt das Verhalten für jeden Browser, jedes Gerät, jeden Identitätsanbieter, jede Eingabe oder jede Deployment-Konfiguration. Lokale Ergebnisse sind keine Staging- oder Produktionsfreigabe.

Automatisierte Testabdeckung ersetzt keine manuellen Prüfungen mit weiteren Identitätsanbietern, assistiven Technologien oder gehosteten Sicherheitskontrollen. Linux-Visual-Baselines gelten nur für Chromium. Das 429-Spike-Verhalten ist durch den letzten vollständigen Lauf nicht belegt, weil dieser Test übersprungen wurde.

## Testdaten und Nachweise

Verwende isolierte Entwicklungs- oder Staging-Dienste und dedizierte Testkonten. Nutze keine persönlichen Konten und dokumentiere keine Passwörter, Tokens, Cookies, E-Mail-Adressen oder andere personenbezogene Daten in Testnachweisen. Halte Datum, Build/Revision, Umgebung, Browser/Gerät oder assistive Technologie, Szenario, Ergebnis und Restrisiken im zugriffsbeschränkten Testnachweis fest. Eine Prüfung bleibt offen, bis ihr Nachweis erfasst und geprüft wurde.
