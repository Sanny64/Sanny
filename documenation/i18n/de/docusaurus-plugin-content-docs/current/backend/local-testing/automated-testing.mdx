## Testbefehle

Führe die Befehle im Repository-Stammverzeichnis aus. Installiere die Playwright-Browser einmalig mit `npx playwright install chromium firefox msedge`.

| Befehl                             | Zweck                                                                   |
| ---------------------------------- | ----------------------------------------------------------------------- |
| `npm run test:backend`             | Backend-Typprüfung sowie Backend-Unit- und Monitoring-Tests.            |
| `npm run test:backend:redis`       | Redis-Session-Integration; Docker muss verfügbar sein.                  |
| `npm run test:e2e:mocked`          | Gemockte Browser-Tests in Chromium, Firefox und Edge.                   |
| `npm run test:e2e:mocked:chromium` | Gemockte Browser-Tests nur in Chromium.                                 |
| `npm run test:e2e:mocked:firefox`  | Gemockte Browser-Tests nur in Firefox.                                  |
| `npm run test:e2e:mocked:edge`     | Gemockte Browser-Tests nur in Edge.                                     |
| `npm run test:e2e`                 | Gemockte und Live-Auth0-E2E-Suites in Chromium, Firefox und Edge.       |
| `npm run test:e2e:real`            | Live-Auth0-Tests in sichtbarem Chromium, Firefox und Edge.              |
| `npm run test:e2e:real:chromium`   | Live-Auth0-Tests nur in sichtbarem Chromium.                            |
| `npm run test:e2e:real:firefox`    | Live-Auth0-Tests nur in sichtbarem Firefox.                             |
| `npm run test:e2e:real:edge`       | Live-Auth0-Tests nur in sichtbarem Edge.                                |
| `npm run test`                     | Root-Gate für Formatierung, Backend, Redis, Frontend und Browser-Tests. |

Der vollständige Gate benötigt Docker, installierte Playwright-Browser, eine erreichbare Entwicklungs-API/Auth0-Umgebung und dedizierte Zugangsdaten `TESTUSER_EMAIL` / `TESTUSER_PASSWORD`. Die Live-Suite verwendet keine persönlichen Konten. `npm run test` enthält Frontend-Lint und App-Builds über `npm run test:frontend`; der Docs-Build bleibt separat. Siehe [Frontend Local Testing](../../frontend/local-testing/automated-testing).

## Was der Gate prüft

| Bereich                             | Automatisierte Nachweise                                                                                                                                          | Grenze                                                                                                                                |
| ----------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| Backend                             | Typprüfung, Unit-Tests, Session-/CSRF-Tests und Redis-Session-Integration.                                                                                        | Kein Penetrationstest und keine Bewertung einer gehosteten Umgebung.                                                                  |
| Öffentliche und authentifizierte UI | Gemockte Playwright-Tests für aktuelle öffentliche Routen, Account-Verknüpfung, Sitzungsaktionen, Settings sowie erlaubte/abgewiesene Admin-Zustände.             | Die meisten API-Antworten sind gemockt; geprüft werden UI-Verhalten und Verträge, nicht die Persistenz des Backends.                  |
| Live-Authentifizierung/Sicherheit   | Dedizierter Auth0-Passwort-Login; Session-Cookie-Attribute; CSRF-Ablehnung bei Profil-, Admin-Rollen- und Logout-Mutationen; erfolgreiches Logout mit CSRF-Token. | Prüft weder den gesamten Live-Account-Lebenszyklus noch erfolgreiche Profil-/Admin-Mutationen.                                        |
| Accessibility                       | `e2e/mock/login-accessibility.spec.ts` und `e2e/mock/sanny-accessibility.spec.ts`: Axe-WCAG-2.2-AA, Tastatur/Fokus, Responsive und Chromium-Baselines.            | Nicht jede Theme-/Browserpräferenz-Kombination wird geprüft. Screenreader, 200%-Zoom und Reduced Motion erfordern manuelle Prüfungen. |
| Visuelle Regression                 | Chromium-Screenshots für Home, Login-Helper, Account-Settings und gefüllte Admin-Ansicht auf Desktop/Mobil sowie eine mobile Settings-Baseline.                   | Screenshot-Baselines belegen keine visuelle Parität zwischen Browsern.                                                                |

## Grenzen und Abschluss

`npm run test` ist ein Regression-Gate für die oben genannten Fälle, aber kein Nachweis, dass jedes Feature, jede Rolle, jeder Provider, jede Präferenz oder jede Sicherheitskontrolle geprüft wurde. Die Rückverfolgbarkeitsmatrix ist noch nicht vollständig. Nicht abgedeckte Kombinationen gelten als unbekannt und nicht als implizit geprüft. Es gibt noch keine gehostete Staging-Umgebung; daher ist eine Staging-Freigabe derzeit nicht möglich.

Bevor eine vollständige Produktverifikation behauptet wird, müssen die folgenden Lücken geschlossen und die Ergebnisse festgehalten werden:

- **Accessibility:** Screenreader testen; 200%-Zoom, Reduced Motion und alle unterstützten Theme-/Zustandskombinationen prüfen. Automatisierte Ansichtsprüfungen ersetzen diese Kontrollen nicht.
- **Google-Provider-Flows:** Google-Login, beide Richtungen der Account-Verknüpfung, Eigentums-Reauthentifizierung, Bestätigen/Abbrechen sowie den resultierenden Auth0-/lokalen Kontostatus manuell prüfen. Der Google-Playwright-Test wird bewusst übersprungen, da Provider kontrollierte Browser blockieren können.
- **Gehostete Sicherheit:** isoliertes Staging, Netzwerk-/Firewall-Grenzen, Auth0-Login/Logout, Account-Lebenszyklus, Refresh-Verhalten, Pagination und Fehlerverträge validieren. Lokale Tests zertifizieren keine Produktionssicherheit.
- **Feature-Rückverfolgbarkeit:** Jedes implementierte Feature und jede Sicherheitskontrolle einem automatisierten Test oder einer dokumentierten manuellen Prüfung zuordnen. Platzhalter und nicht unterstütztes Verhalten ausdrücklich kennzeichnen.

Offene manuelle Prüfungen und Deployment-Aufgaben stehen in `backend/TODO.md` im Repository. Gehostete Verifikationsnachweise gehören in [Monitoring and Verification](../monitoring.mdx); lokale Tests und CI-Ergebnisse sind keine Staging-Freigabe.

## Screenshot-Baselines

Die Baselines sind Chromium-spezifisch und liegen bei der E2E-Spezifikation. Nach einer beabsichtigten visuellen Änderung:

```sh
npx playwright test e2e/mock/sanny-accessibility.spec.ts --project=chromium --grep "visual baseline" --update-snapshots
```

Prüfe die geänderten Bilder, bevor du Baselines akzeptierst.

Siehe Googles [Hinweise zur Anmeldung mit unterstützten Browsern](https://support.google.com/accounts/answer/7675428?hl=de) und Playwrights Empfehlung, [Drittanbieter-Abhängigkeiten nicht zu testen](https://playwright.dev/docs/best-practices#avoid-testing-third-party-dependencies).
