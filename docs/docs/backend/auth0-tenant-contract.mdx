# Auth0 Tenant Contract

Tenant configuration is managed in Auth0 and must be verified independently of the source code. Never put client secrets, database passwords, certificates, private keys, or access tokens in this document.

## Verification Status

Source contracts and automated tests verify local OAuth and token behavior. The hosted Auth0 tenant still requires an authorized staging review. Mark a check complete only after verifying the intended tenant and recording the date and outcome in the restricted deployment record. Keep tenant identifiers and reviewer details out of public docs.

## Browser Authentication

- The backend creates a PKCE verifier and `S256` challenge for every login. Configure the tenant to use Authorization Code Flow with PKCE and `S256`.
- Register only the exact HTTPS callback, success, and logout URLs for each deployment.
- Enable refresh-token rotation and reuse detection according to the tenant policy.
- Allow the `offline_access` scope for the application.
- Deploy the Database Actions and connect them to the intended MariaDB database.

## API and Claims

- The API identifier must match `AUTH0_AUDIENCE`.
- Tokens must have the configured issuer and audience, a non-empty `sub`, valid expiry, and valid signature.
- Read permissions from the `permissions` claim or, when absent, OAuth `scope`.
- Roles, email, and name use configured custom-claim namespaces. The reserved `https://example.invalid/` namespace is for documentation examples only; the tenant Action and API configuration must use the same actual namespace. `AUTH0_ROLES_CLAIM` and email/name overrides may change it. Standard `email` and `name` claims are fallbacks.
- Local account creation requires `email_verified === true`.
- Missing required permissions or roles must deny access. Email and name must never grant permissions.
- The Login Action `roleClaims.js` assigns the Auth0 `user` role to non-Database users when needed and includes it in the roles claim. `AUTH0_DEFAULT_ROLE_ID` must match the reviewed role. The M2M app needs `update:users`; Database registration continues to use `assignDefaultUserRole.js`.

## Privileged Management API

- Keep role synchronization disabled unless `AUTH0_ROLE_SYNC_ENABLED=true` is explicitly intended.
- When enabled, administrators with `write:users` and recent MFA may assign any role present in Auth0; there is no role allowlist.
- Grant the M2M application only the minimum Management API permissions required.

## MFA Step-Up and Password Reset

- Deploy `backend/auth0/post-login/mfaStepUp.js` in the Login flow. Set `MFA_ACR` to `http://schemas.openid.net/pape/policies/2007/06/multi-factor`. The Action requests MFA only when that value is explicitly requested.
- Enable the intended factors under **Security > Multi-factor Auth**. If Actions customize the factor selection, enable **Customize MFA Factors using Actions**.
- User password reset requires a valid Sanny session but no MFA step-up. Admin reset additionally requires the admin role, `write:users`, and MFA within the last 15 minutes.
- Both handlers create a Management API `/tickets/password-change` ticket using `AUTH0_CLIENT_ID`, `AUTH0_DATABASE_CONNECTION_ID`, and the stored user email. The non-secret `con_` connection ID must match the configured Database Connection, which must be enabled for the application. The M2M client needs `create:user_tickets`.
- Tickets expire after 15 minutes, do not mark email as verified, and must not put email in redirects. The redirect target uses only the stored user email. Social-only accounts reset passwords at their identity provider.
- Sanny sends bilingual plain-text mail through SMTP. Port 465 uses implicit TLS; other ports use STARTTLS. Certificate verification must remain enabled. SMTP acceptance alone does not verify mailbox delivery.
- Do not use the public `/dbconnections/change_password` endpoint. Bot Detection errors there cannot be interactively completed by a server-side call. Do not disable Bot Detection.
- Reset endpoints return safe `502` errors or `429` on rate limiting; SMTP errors return safe `503`. An Auth0 `401` must not be surfaced as a Sanny session `401`.

## Linked Identities and Canonical Subjects

- Deploy `backend/auth0/post-login/linkAccounts.js` in the Auth0 Login flow. Backend or container deployment does not deploy Actions.
- On later Database logins, the Action must call `api.authentication.setPrimaryUser` when the verified Google primary identity contains that Database identity. Existing `confirmed` metadata must not skip canonicalization.
- If identities remain unlinked, require ownership proof again even when metadata says `confirmed`. Only a current `pending` state suppresses duplicate prompts for five minutes.
- Secondary ownership-proof logins (`link_proof=true`) intentionally retain the Database subject and must not be canonicalized before verification.
- Google is the canonical primary identity. Ownership proof is required for the other account. The backend checks the exact `proofUserId`; the signed proof contains `authenticatedUserId`.
- Deploy Actions and backend together. If `account_linking_needed` occurs despite a stored Google identity, inspect the token subject and deployed Action version. Do not bypass the check by reversing link validation or rewriting local subjects.
- If linking is not offered, verify both accounts have `email_verified: true`, the providers are enabled, and the Action is active in the Login flow. Set `ACCOUNT_LINK_CONFIRMATION_URL` per environment to the backend `/api/v001/auth/confirm-account-linking` route.

### Password Reset During Ownership Proof

- Local tests may set the Auth0 Application Login URI to `https://localhost:5174/account-link-proof-resume`. Production must use the equivalent route on the deployed login frontend. This is not the OAuth callback URL.
- The popup stores opaque pending state and expiry in `sessionStorage`. After reset, that popup resumes ownership proof through the resume route.
- Password reset alone is not ownership proof. Expired state requires restarting linking; a reset in another tab does not resume the original popup automatically.
- Continuations use `AUTH0_DOMAIN`. Do not mix tenant and custom domains within one Auth0 transaction.
