# Set up the Auth0 tenants

This procedure configures Auth0 for the existing Sanny backend. It follows the
repository's current OAuth, custom database, token-claim, account-linking, and
MFA contracts. Complete it once for each environment you operate (e.g. `test` vs. `prod` tenants).

Auth0 hosts the login and runs the custom database scripts, but the Sanny
database remains the user store.

## 1. Create a tenant in auth0 (preferibly EU)

For instructions look here: [Auth0 Docs](https://auth0.com/docs/get-started/auth0-overview/create-tenants)

## 2. Create a SPA application

In **Applications > Applications** -> **`+ Create Application`**: Single Page Web Application

Record it's Client ID, and Client Secret as `AUTH0_CLIENT_ID` and `AUTH0_CLIENT_SECRET` in your `backend/.env`

In the application's settings:

| Setting                | Local development example                                                                                       | Production value                                                                                                |
| ---------------------- | --------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| Application Login URI  | https://localhost:5174                                                                                          | https://auth.example.de                                                                                         |
| Allowed Callback URLs  | https://localhost:8443/api/v001/auth/callback, https://localhost:8443/api/v001/auth/account-link-proof/callback | https://api.example.de/api/v001/auth/callback, https://api.example.de/api/v001/auth/account-link-proof/callback |
| Allowed Logout URLs    | https://localhost:5173                                                                                          | https://example.de                                                                                              |
| Allowed Web Origins    | https://localhost:5173                                                                                          | https://example.de                                                                                              |
| Allowed Origins (CORS) | https://localhost:5173, https://localhost:5174                                                                  | https://example.de, https://auth.example.de                                                                     |

Enabled Toggles:

- Allow Cross-Origin Authentication
- Allow Google One Tap
- Set Idle Refresh Token Lifetime
- Allow Refresh Token Rotation

I recommend also adding a fitting name and your `favicon.ico` here, as it will be visible during login.
Your favicon can be added by uploading it to **imgur** for example and adding its URL to the application.

## 3. Create a M2M application

In **Applications > Applications** -> **`+ Create Application`**: Machine to Machine

Record it's Client ID, and Client Secret as `AUTH0_M2M_CLIENT_ID` and `AUTH0_M2M_CLIENT_SECRET` in your `backend/.env`

## 4. Create an API

In **Applications > APIs** -> **`+ Create API`**. The identifier can be a URI; it does not need
to resolve in a browser. Configure it to sign access tokens with RS256.

Record it's identifier as `AUTH0_AUDIENCE` in your `backend/.env`.

In settings enabled toggles:

- Enable RBAC
- Add Permissions in the Access Token
- Allow Offline Access

In Permissions:

- Add the API permissions used by the backend:

| Permission     | Use                                  |
| -------------- | ------------------------------------ |
| `update:me`    | Update the signed-in user's profile  |
| `delete:me`    | Delete the signed-in user's profile  |
| `read:users`   | Read user profiles (admin)           |
| `write:users`  | Create users or manage roles (admin) |
| `update:users` | Update users (admin)                 |
| `delete:users` | Delete users (admin)                 |

In Application Access:
Your M2M client -> Edit -> User-Delegated Access: `read:users`, `write:users`, `delete:users`

## 4. Edit your Management API access

In **Applications > APIs** look for `Auth0 Management API`. Head to `Application Access`:

Your M2M client -> Edit -> Client Access: `read:users`, `update:users`, `delete:users`, `create:user_tickets`, `read:roles`

Record it's identifier as `AUTH0_MGMT_AUDIENCE` in your `backend/.env`.

- In your backend/.env you must add `/api/v2/` behind the identifier.

## 5. Configure the custom database connection

In **Authentication > Database** -> **`+ Create DB connection`**

### During creation enable toggles:

- Email address
- Username
- Password

### In Settings enabled toggles:

- Sync user profile attributes at each login
- Improved brute force protection

### In Attributes:

- Email -> Configure:
  - Use email as Identifier: yes
  - Verification Method: OTP
  - Allow Signup with Email: Required
  - Verify email on sign up: yes
  - Require email on user profile: yes.
- `+ Add Attribute` ->
  - Username: Use username as Identifier: no
  - Allow Signup with Username: Required
  - Require Username on user profile: yes
  - Username Length: 3-30.

### In Authentication:

- Password -> Configure:
  - Password for login: allow
  - Password on signup: allow
  - Self-service change password: allow
  - Minimum password length: 15
  - Additional composition rules -> Toggle all.
  - Maximum password length exceeded: Show error.

### In Custom Database:

- Enabled Toggles:
  - Use my own database

`backend/auth0/database-action/`:

| Auth0 script    | Repository file     |
| --------------- | ------------------- |
| Login           | `login.js`          |
| Get User        | `getUser.js`        |
| Create          | `create.js`         |
| Verify          | `verify.js`         |
| Change Password | `changePassword.js` |
| Delete          | `delete.js`         |

Provide these connection configuration values to the scripts:

| Configuration key | Value                                                               |
| ----------------- | ------------------------------------------------------------------- |
| `DB_HOST`         | Database hostname reachable from Auth0's custom database runtime    |
| `DB_PORT`         | Database port, normally `3306`                                      |
| `DB_USER`         | Dedicated database account with only the required user-table access |
| `DB_PASSWORD`     | Secret for that database account                                    |
| `DB_NAME`         | Database containing the Prisma `User` table                         |
| `DB_SSL_CA`       | Trusted CA certificate for the database TLS connection              |

The scripts require TLS certificate validation; do not disable it.

Use the dashboard's **Try** controls to test every script against a non-production test user before
connecting a production database.

See [the script contract](./auth0-database-action-scripts)
for the expected inputs and callback behavior.

In Applications:

- Toggle on your Single Page Application

For more info on the database actions scripts see here: [Auth0 Database Action Scripts](./auth0-database-action-scripts)

## 6. Configure Google login

In **Authentication > Social**, configure the Google connection using the
Google OAuth client credentials, then enable it for the same Single Page
Application. As for now do not add any other social logins but Google OAuth2.

Find more information here: [Auth0 docs](https://auth0.com/docs/authenticate/identity-providers/social-identity-providers/google)

### Toggles:

- Purpose: Authentication
- Permissions: Offline Access
- Advanced: Sync user profile attributes at each login: yes

### In applications:

- Toggle your Single Page Application

## 7. Authentication Profile

- You must select `Identifier first`.

## 8. User roles

In **User Management > Roles** -> `+ Create role`:

- user -> permissions: `update:me`, `delete:me`
- admin -> permissions: all

## 9. Custom Domain

- In **Branding > Custom Domains**: Add custom domain
  - alternatively don't, but this must be reflected in your backend/.env in AUTH0_DOMAIN

## 10. Setup Email Provider

- Depending on your setup at a email provider after your liking.
  - Some web hosting service like [Hetzner](https://www.hetzner.com) offer you a free SMTP server to use alongside your web domain.

## 11. Security

- Attack Protection: Enable all
- Multi-factor Auth: Enable One-time Password, Email and Recovery Code
  - Require Multi-factor Auth: Never
  - MFA Risk Assessors: Enable Adaptive MFA Risk Assessment: yes
  - Additional settings: Customize MFA Factors using Actions: yes

## 12. Deploy the Actions

In **Actions > Library:** Create Actions from the repository files

1. `verifyEmail.js`
2. `linkAccounts.js`
3. `mfaStepUp.js`
4. `roleClaims.js`
5. `assignDefaultUserRole.js`

**!! Changes in the environment variables below must be reflected in the backend/.env and all scripts !!**

### `verifyEmail.js`

Required Action secrets:

| Secret                       | Value                                                         |
| ---------------------------- | ------------------------------------------------------------- |
| `AUTH0_DOMAIN`               | Auth0 domain hostname, without `https://` or a trailing slash |
| `AUTH0_M2M_CLIENT_ID`        | Actions Management API client ID                              |
| `AUTH0_M2M_CLIENT_SECRET`    | Actions Management API client secret                          |
| `AUTH0_MGMT_AUDIENCE`        | `https://<AUTH0_DOMAIN>/api/v2/`                              |
| `AUTH0_EMAIL_VERIFIED_CLAIM` | `https://sanny64.app/email_verified`                          |

### `linkAccounts.js`

Required Action secrets:

| Secret                                                                      | Value                                                         |
| --------------------------------------------------------------------------- | ------------------------------------------------------------- |
| `AUTH0_DOMAIN`                                                              | Same Auth0 domain hostname as the application                 |
| `AUTH0_M2M_CLIENT_ID`                                                       | Actions Management API client ID                              |
| `AUTH0_M2M_CLIENT_SECRET`                                                   | Actions Management API client secret                          |
| `AUTH0_MGMT_AUDIENCE`                                                       | `https://<AUTH0_DOMAIN>/api/v2/`                              |
| `NODE_ENV`                                                                  | Exactly `development` or `production`                         |
| `DEV_ACCOUNT_LINK_CONFIRMATION_URL` or `PROD_ACCOUNT_LINK_CONFIRMATION_URL` | The matching backend confirmation endpoint from the URL table |
| `ACCOUNT_LINK_ALLOWED_PROVIDERS`                                            | `auth0,google-oauth2`                                         |

Set only the URL secret for the environment used by this Action deployment,
matching its `NODE_ENV`. The Login flow is tenant-wide, so one deployed Action
cannot select a different environment per application. The Action requires a
recent `pending` decision before suppressing a repeat confirmation; do not
bypass proof or enable automatic linking.

### `mfaStepUp.js`

Set these Action secrets exactly; the backend sends these ACR values when
requesting step-up:

| Secret          | Value                                                          |
| --------------- | -------------------------------------------------------------- |
| `MFA_ACR`       | `http://schemas.openid.net/pape/policies/2007/06/multi-factor` |
| `EMAIL_MFA_ACR` | `https://example.de/acr/email-otp`                             |

Enable the intended factors in **Security > Multi-factor Auth**. The Action
requests MFA only when the backend explicitly includes the matching ACR value.
If using Action-based MFA factor customization, enable **Customize MFA Factors
using Actions** under the MFA additional settings.

### `roleClaims.js`

Required Action secrets:

| Secret                       | Value                                         |
| ---------------------------- | --------------------------------------------- |
| `AUTH0_CLAIM_NAMESPACE`      | `https://example.app`                         |
| `AUTH0_EMAIL_VERIFIED_CLAIM` | `https://example.app/email_verified`          |
| `AUTH0_DOMAIN`               | Same Auth0 domain hostname as the application |
| `AUTH0_M2M_CLIENT_ID`        | Actions Management API client ID              |
| `AUTH0_M2M_CLIENT_SECRET`    | Actions Management API client secret          |
| `AUTH0_MGMT_AUDIENCE`        | `https://<AUTH0_DOMAIN>/api/v2/`              |
| `AUTH0_DEFAULT_ROLE_ID`      | ID of the reviewed Auth0 role named `user`    |

This Action puts roles, email, and name into the access token as
`https://example.app/roles`, `https://example.app/email`, and
`https://example.app/name`. The backend's default claim names match these
values. If you change the namespace, update the backend's corresponding
`AUTH0_ROLES_CLAIM`, `AUTH0_EMAIL_CLAIM`, `AUTH0_NAME_CLAIM`, and
`AUTH0_EMAIL_VERIFIED_CLAIM` settings at the same time.

### `assignDefaultUserRole.js`

Required Post User Registration Action secrets:

- `AUTH0_DOMAIN`
- `AUTH0_M2M_CLIENT_ID`
- `AUTH0_M2M_CLIENT_SECRET`
- `AUTH0_MGMT_AUDIENCE`
- `AUTH0_DEFAULT_ROLE_ID`

Use the same reviewed `user` role ID as `roleClaims.js`. This Action assigns
that role to database users at registration; `roleClaims.js` assigns it to
non-database users if they do not already have it.

# 13. Configure Triggers

Head to **Actions > Triggers**:

- **post-login:**
  In this order: Verify Email -> Link Accounts -> MFA step up -> Role claims

- **post-user-registration:**
  Assign default user role
