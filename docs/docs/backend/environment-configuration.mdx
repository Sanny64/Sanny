# Environment Configuration Guide

This guide explains how to properly configure the application for different environments (development vs. production) using Auth0.

## Overview

The application requires common Auth0/database settings plus environment-specific URLs. `NODE_ENV` must be exactly `development` or `production`; URL and proxy settings use the matching `DEV_` or `PROD_` prefix. Examples below are placeholders using reserved domains, not working credentials or deployment values.

- **NODE_ENV**: Controls production mode (`production` or `development`)
- **AUTH0_DOMAIN**: Your Auth0 tenant domain
- **AUTH0_CLIENT_ID**: Auth0 application client ID
- **AUTH0_CLIENT_SECRET**: Auth0 application client secret
- **AUTH0_AUDIENCE**: Auth0 API audience identifier
- **DEV\_/PROD_AUTH0_CALLBACK_URL**: OAuth callback URL (must be registered in Auth0)
- **DEV\_/PROD_AUTH0_SUCCESS_REDIRECT** and **DEV\_/PROD_AUTH0_LOGOUT_REDIRECT**: approved frontend destinations
- **DEV\_/PROD_ACCOUNT_LINK_FRONTEND_URL**: login frontend account-linking page
- **DEV\_/PROD_CORS_ORIGINS**: comma-separated exact origins
- **DEV\_/PROD_TRUST_PROXY**: `false`, `true`, or trusted proxy IP/CIDR; numeric hop counts are unsupported

## Development Environment Setup

### Environment Variables

For local Docker development, put required values in the backend environment file. Do not copy this example literally; generate local secrets and use isolated development services.

```bash
# Common backend settings
NODE_ENV=development
AUTH0_DOMAIN=tenant.example.invalid
AUTH0_CLIENT_ID=replace-with-development-client-id
AUTH0_CLIENT_SECRET=replace-with-development-client-secret
AUTH0_AUDIENCE=https://api.example.com
DATABASE_URL=mysql://<user>:<password>@<private-host>:3306/<database>
REDIS_PASSWORD=replace-with-a-random-local-secret

# Development-specific URL and proxy settings
DEV_AUTH0_CALLBACK_URL=https://localhost:8443/api/v001/auth/callback
DEV_AUTH0_SUCCESS_REDIRECT=http://localhost:5173/
DEV_AUTH0_LOGOUT_REDIRECT=http://localhost:5173/
DEV_ACCOUNT_LINK_FRONTEND_URL=http://localhost:5174/confirm-linking
DEV_CORS_ORIGINS=http://localhost:5173,http://localhost:5174
DEV_TRUST_PROXY=false

# Optional privileged feature; keep disabled unless intentionally tested
AUTH0_ROLE_SYNC_ENABLED=false
```

### Auth0 Development Tenant Setup

1. **Create a new Auth0 application** for your development tenant:
   - Application type: `Regular Web Application`

- Name: `Example Development Application`

2. **Configure OAuth settings**:
   - Allowed Callback URLs:
     - `https://localhost:8443/api/v001/auth/callback`
   - Allowed Logout URLs:
     - `http://localhost:5173/`
   - Allowed Web Origins (CORS):
     - `https://localhost:8443`
     - `http://localhost:5173`
     - `http://localhost:5174`

3. **Configure Database Connections**:
   - Enable "Username-Password-Authentication"
   - Create a custom database connection with the provided scripts:
     - `create.js` - User creation and signup
     - `login.js` - User login
     - `getUser.js` - Fetch user by ID
     - `delete.js` - User deletion with linked account cleanup
     - `verify.js` - Email verification (optional)

4. **Create Post-Login Action**:
   - Name: `linkAccount` or `Post-Login Actions`
   - Trigger: `Post-Login`
   - Includes linking logic and email verification claim stamping

5. **Create another Post-Login Action**:
   - Name: `roleClaims`
   - Trigger: `Post-Login`
   - Stamps custom claims (roles, email_verified) on access tokens

6. **Create an MFA step-up Action**:
   - Name: `mfaStepUp`
   - Trigger: `Post-Login`
   - Deploy `backend/auth0/post-login/mfaStepUp.js`
   - Set the Action secrets `MFA_ACR` to
     `http://schemas.openid.net/pape/policies/2007/06/multi-factor` and
     `EMAIL_MFA_ACR` to `https://example.invalid/acr/email-otp` for this documentation example; configure the actual namespace in the Auth0 tenant.
   - Enable the factors used for admin step-up and the Email factor in
     **Security > Multi-factor Auth**. Self-service password resets request
     the Email factor only; users must have a verified, enrolled email factor.
   - Bind this Action before enabling admin reauthentication or self-service
     password reset. It handles the standard MFA request with any enrolled
     factor and the email ACR with an email OTP challenge only.

7. **Create a Post User Registration Action**:
   - Name: `assignDefaultUserRole`
   - Trigger: `Post User Registration`
   - Deploy `backend/auth0/post-user-registration/assignDefaultUserRole.js`
   - Add Action secrets: `AUTH0_DOMAIN`, `AUTH0_M2M_CLIENT_ID`,
     `AUTH0_M2M_CLIENT_SECRET`, `AUTH0_MGMT_AUDIENCE`, and
     `AUTH0_DEFAULT_ROLE_ID` (the Auth0 `user` role ID)

8. **Management API Configuration**:
   - Grant read/write permissions for roles and users
   - Scopes needed:
     - `read:users`
     - `update:users`
     - `read:roles`
     - `update:user_app_metadata`
     - `create:user_identities`
     - `delete:users`
   - The M2M application used by `assignDefaultUserRole` only needs
     `update:users`.

### Frontend Service URLs (Development)

- **Main application**: `http://localhost:5173`
- **Login/Auth application**: `http://localhost:5174`
- **Backend API**: `https://localhost:8443`

Start services with:

```bash
# Terminal 1 - Backend (from repository root)
npm run start:backend

# Terminal 2 - Main frontend
cd sanny
npm run dev

# Terminal 3 - Login frontend
cd login
npm run dev
```

## Production Environment Setup

### Environment Variables

For production deployment, use these settings in your production `.env`:

```bash
# Compose sets NODE_ENV=production for the production service.
# Common settings (load from the production secret store)
AUTH0_DOMAIN=tenant.example.invalid
AUTH0_CLIENT_ID=replace-with-production-client-id
AUTH0_CLIENT_SECRET=replace-with-production-client-secret
AUTH0_AUDIENCE=https://api.example.com
DATABASE_URL=mysql://<user>:<password>@<private-host>:3306/<database>
REDIS_PASSWORD=replace-with-a-production-secret

# Production URL and proxy settings (replace reserved example origins)
PROD_AUTH0_CALLBACK_URL=https://api.example.com/api/v001/auth/callback
PROD_AUTH0_SUCCESS_REDIRECT=https://app.example.com/
PROD_AUTH0_LOGOUT_REDIRECT=https://app.example.com/
PROD_ACCOUNT_LINK_FRONTEND_URL=https://login.example.com/confirm-linking
PROD_CORS_ORIGINS=https://app.example.com,https://login.example.com
PROD_TRUST_PROXY=192.0.2.10
ENABLE_SWAGGER=false
AUTH0_ROLE_SYNC_ENABLED=false
```

### Auth0 Production Tenant Setup

1. **Create a production Auth0 application**:
   - Application type: `Regular Web Application`

- Name: `Example Production Application`

2. **Configure OAuth settings**:
   - Allowed Callback URLs:
   - `https://api.example.com/api/v001/auth/callback`
   - Allowed Logout URLs:
   - `https://app.example.com/`
   - Allowed Web Origins (CORS):
   - `https://app.example.com`
   - `https://login.example.com`

3. **Configure Database Connections**:
   - Same scripts as development, but ensure they use production database credentials
   - **NEVER share dev/prod database credentials**

4. **Post-Login Actions**:
   - Deploy the same actions as development
   - Ensure claims use production domains:
   - Use the same custom-claim namespace in the tenant and token consumers; the actual namespace is deployment configuration and is intentionally not included here.

5. **Management API Configuration**:
   - Same scopes as development (see above)

### Production Domain Setup

- **Main application**: `https://app.example.com`
- **Auth/Login application**: `https://login.example.com`
- **Backend API**: `https://api.example.com`

### Deployment with NGINX

The backend runs behind an NGINX reverse proxy:

```nginx
upstream backend {
    server localhost:3000;
}

server {
    listen 443 ssl http2;
    server_name api.example.com;

    ssl_certificate /path/to/deployment-certificate.crt;
    ssl_certificate_key /path/to/deployment-private-key.key;

    # Set trust proxy for forwarded headers
   proxy_set_header X-Forwarded-For $remote_addr;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_set_header Host $host;

    location / {
        proxy_pass http://backend;
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";
    }
}
```

## Environment Variable Priority

The application follows this priority when loading URLs:

### Development (NODE_ENV != "production")

1. Read the environment-specific value (for example, `DEV_AUTH0_CALLBACK_URL`).
2. Required callback, redirect, account-link frontend, and CORS values do not have application defaults.

### Production (NODE_ENV == "production")

1. Env variable must be set and be a valid HTTPS URL
2. No defaults allowed - validation will fail if variables are missing or invalid

## Account Linking URL Configuration

Account linking uses `DEV_ACCOUNT_LINK_FRONTEND_URL` or `PROD_ACCOUNT_LINK_FRONTEND_URL`, selected using `NODE_ENV`:

- **Development example**: `http://localhost:5174/confirm-linking`
- **Production example**: `https://login.example.com/confirm-linking` (must use the deployed HTTPS origin)

The backend automatically constructs the full URL with query parameters.

## Validation

The application validates all production configuration on startup. If required variables are missing or invalid, the server will fail to start with a clear error message.

To verify your configuration before starting:

```bash
cd backend
npm run type-check  # Verify TypeScript types
npm test            # Run automated tests
```

## Troubleshooting

### "AUTH0_DOMAIN must be a hostname" error

- Ensure `AUTH0_DOMAIN` is just the domain (e.g., `your-tenant.auth0.com`), not a full URL

### "must use HTTPS in production" error

- In production, all Auth0 URLs must start with `https://`
- This check only applies when `NODE_ENV=production`

### CORS errors in development

- Verify your frontend URL is in `CORS_ORIGINS`
- Common issue: `http://127.0.0.1` vs `http://localhost` mismatch

### Account linking redirects to wrong URL

- Verify the `DEV_` or `PROD_ACCOUNT_LINK_FRONTEND_URL` value selected by `NODE_ENV`.
- Production values must use HTTPS and match the registered Auth0 redirect origins.

### Role sync returning 503

- Check `AUTH0_ROLE_SYNC_ENABLED=true` in production `.env`
- Check Auth0 Management API credentials

When role sync is enabled, the backend accepts any role name that exists in Auth0; there is no assignable-role allowlist. The endpoint is restricted to admins with `write:users` permission and recent MFA. Enable this mode only if that policy is intended.

## Security Considerations

1. **Never commit `.env` to version control**
2. **Use strong secrets** for Auth0 client credentials, Redis, database access, and any enabled Auth0 Management API integration.
3. **Rotate credentials regularly**, especially if exposed
4. **Use separate Auth0 tenants** for development and production
5. **Restrict CORS origins** to only necessary domains
6. **Enable HTTPS in production** - the app enforces this
7. **Use environment-specific database URLs** to prevent accidents
8. **Audit Auth0 connections** regularly for unauthorized changes
