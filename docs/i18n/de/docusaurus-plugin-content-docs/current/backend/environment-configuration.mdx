# Umgebungskonfiguration

## Überblick

Die Konfiguration besteht aus gemeinsamen Zugangsdaten und umgebungsspezifischen URLs. `NODE_ENV` muss exakt `development` oder `production` sein. Für URL- und Proxy-Einstellungen wählt das Backend abhängig davon den Präfix `DEV_` oder `PROD_`. Die folgenden Werte sind Beispiele mit reservierten Domains, keine verwendbaren Zugangsdaten oder Zielsysteme.

Gemeinsame Backend-Variablen:

- `AUTH0_DOMAIN`: Auth0-Hostname ohne Schema oder Pfad.
- `AUTH0_AUDIENCE`: API-Identifier.
- `AUTH0_CLIENT_ID` und `AUTH0_CLIENT_SECRET`: Zugangsdaten der vertraulichen Anwendung.
- `DATABASE_URL`: private MariaDB-Verbindung.
- `REDIS_PASSWORD`: lokales bzw. produktives Redis-Geheimnis. Compose erstellt daraus die TLS-Verbindung.
- `AUTH0_ROLE_SYNC_ENABLED`: optionale privilegierte Funktion; standardmäßig deaktiviert lassen.

| Einstellung                       | Entwicklung                                                                         | Produktion                                                                             |
| --------------------------------- | ----------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| Laufzeit                          | `NODE_ENV=development`                                                              | Compose setzt `NODE_ENV=production`                                                    |
| Callback, Erfolgs- und Logout-URL | `DEV_AUTH0_CALLBACK_URL`, `DEV_AUTH0_SUCCESS_REDIRECT`, `DEV_AUTH0_LOGOUT_REDIRECT` | `PROD_AUTH0_CALLBACK_URL`, `PROD_AUTH0_SUCCESS_REDIRECT`, `PROD_AUTH0_LOGOUT_REDIRECT` |
| Account-Link-Frontend             | `DEV_ACCOUNT_LINK_FRONTEND_URL`                                                     | `PROD_ACCOUNT_LINK_FRONTEND_URL`                                                       |
| CORS                              | `DEV_CORS_ORIGINS` mit exakten lokalen Origins                                      | `PROD_CORS_ORIGINS` mit ausschließlich HTTPS-Origins                                   |
| Proxy-Vertrauen                   | `DEV_TRUST_PROXY=false`                                                             | `PROD_TRUST_PROXY` passend zum vertrauenswürdigen Proxy                                |

`TRUST_PROXY` akzeptiert `false`, `true` oder eine IP-/CIDR-Angabe. Numerische Hop-Zahlen werden nicht unterstützt. Produktions-URLs müssen HTTPS verwenden. Produktionsstart schlägt fehl, wenn erforderliche Zugangsdaten, URLs oder CORS-Angaben fehlen.

## Lokale Entwicklung

Speichere echte lokale Werte nur in der ignorierten Backend-Umgebungsdatei. Nutze separate Entwicklungsdienste und kopiere keine Produktionszugangsdaten.

```dotenv
NODE_ENV=development
AUTH0_DOMAIN=tenant.example.invalid
AUTH0_CLIENT_ID=replace-with-development-client-id
AUTH0_CLIENT_SECRET=replace-with-development-client-secret
AUTH0_AUDIENCE=https://api.example.com
DATABASE_URL=mysql://<user>:<password>@<private-host>:3306/<database>
REDIS_PASSWORD=replace-with-a-random-local-secret

DEV_AUTH0_CALLBACK_URL=https://localhost:8443/api/v001/auth/callback
DEV_AUTH0_SUCCESS_REDIRECT=http://localhost:5173/
DEV_AUTH0_LOGOUT_REDIRECT=http://localhost:5173/
DEV_ACCOUNT_LINK_FRONTEND_URL=http://localhost:5174/confirm-linking
DEV_CORS_ORIGINS=http://localhost:5173,http://localhost:5174
DEV_TRUST_PROXY=false
AUTH0_ROLE_SYNC_ENABLED=false
```

Die Beispiele `tenant.example.invalid` und `api.example.com` sind reserviert und müssen durch Werte einer isolierten Testumgebung ersetzt werden. Richte Auth0-Callbacks, Logout-URLs, Web Origins, Database Actions und Management-API-Berechtigungen gemäß [Auth0-Tenant-Vertrag](./auth0-tenant-contract.mdx) ein.

Die lokalen Frontends verwenden `http://localhost:5173` und `http://localhost:5174`; die Backend-API läuft über `https://localhost:8443`. Starte das Backend aus dem Repository-Stammverzeichnis mit `npm run start:backend`. Die Frontends können jeweils mit `npm run dev` in ihren Verzeichnissen gestartet werden.

## Produktionskonfiguration

In der Produktions-Compose-Datei wird `NODE_ENV=production` gesetzt. Lade gemeinsame Zugangsdaten aus dem Produktions-Secret-Store und ersetze alle reservierten Beispielwerte:

```dotenv
AUTH0_DOMAIN=tenant.example.invalid
AUTH0_CLIENT_ID=replace-with-production-client-id
AUTH0_CLIENT_SECRET=replace-with-production-client-secret
AUTH0_AUDIENCE=https://api.example.com
DATABASE_URL=mysql://<user>:<password>@<private-host>:3306/<database>
REDIS_PASSWORD=replace-with-a-production-secret

PROD_AUTH0_CALLBACK_URL=https://api.example.com/api/v001/auth/callback
PROD_AUTH0_SUCCESS_REDIRECT=https://app.example.com/
PROD_AUTH0_LOGOUT_REDIRECT=https://app.example.com/
PROD_ACCOUNT_LINK_FRONTEND_URL=https://login.example.com/confirm-linking
PROD_CORS_ORIGINS=https://app.example.com,https://login.example.com
PROD_TRUST_PROXY=192.0.2.10
ENABLE_SWAGGER=false
AUTH0_ROLE_SYNC_ENABLED=false
```

`example.com` und `192.0.2.10` sind Dokumentationsbeispiele, keine Zielwerte. Die Auth0-Domain muss als Hostname ohne `https://` eingetragen werden. Der Proxy-Eintrag muss der tatsächlich vertrauenswürdigen NGINX-Adresse bzw. dem freigegebenen CIDR entsprechen. Fastify darf nicht direkt aus nicht vertrauenswürdigen Netzen erreichbar sein.

Das Backend erwartet, dass NGINX TLS beendet, HTTP auf HTTPS umleitet und Forwarding-Header selbst setzt. Verwende keine vom Client übernommenen `X-Forwarded-*`-Werte. Die Host-Firewall muss Backend, Redis und Monitoring-Endpunkte vor öffentlichem Zugriff schützen. Details zur Freigabe stehen in [Bereitstellung und Wiederherstellung](./deployment.mdx) sowie [Monitoring und Verifizierung](./monitoring.mdx).

## Account-Verknüpfung und Rollen-Synchronisierung

`DEV_ACCOUNT_LINK_FRONTEND_URL` bzw. `PROD_ACCOUNT_LINK_FRONTEND_URL` bezeichnet das Login-Frontend. Davon getrennt zeigt das Auth0-Action-Secret `DEV_ACCOUNT_LINK_CONFIRMATION_URL` bzw. `PROD_ACCOUNT_LINK_CONFIRMATION_URL` auf die Backend-Route zur Bestätigung der Verknüpfung. Die Werte müssen zur Umgebung und zum bereitgestellten Action-Code passen.

Wenn `AUTH0_ROLE_SYNC_ENABLED=true` gesetzt ist, kann ein berechtigter Administrator jede in Auth0 vorhandene Rolle zuweisen; es gibt keine Allowlist. Der Endpunkt erfordert Admin-Rolle, `write:users` und kürzlich abgeschlossene MFA. Aktiviere diese Funktion nur nach expliziter Prüfung dieser Richtlinie.

## Prüfung und Fehlerbehebung

```bash
cd backend
npm run type-check
npm test
```

- **Ungültiger Auth0-Hostname:** Nur den Tenant-Hostnamen ohne Schema, Port oder Pfad eintragen.
- **HTTPS-Validierung schlägt fehl:** In Produktion müssen Callback, Redirects, Account-Link-Frontend und CORS HTTPS verwenden.
- **CORS-Fehler lokal:** Origin exakt mit `DEV_CORS_ORIGINS` vergleichen; `localhost` und `127.0.0.1` sind verschiedene Origins.
- **Account-Linking leitet falsch weiter:** Den durch `NODE_ENV` gewählten `DEV_`- oder `PROD_ACCOUNT_LINK_FRONTEND_URL`-Wert prüfen.
- **Rollen-Synchronisierung liefert `503`:** Feature-Flag, Management-API-Zugangsdaten und minimal erforderliche Berechtigungen prüfen. Die Funktion nicht aktivieren, um andere Fehler zu umgehen.

## Sicherheitscheckliste

- `.env`-Dateien und Secrets niemals committen oder in Logs ausgeben.
- Für Entwicklung und Produktion getrennte Auth0-, Datenbank- und Redis-Ressourcen verwenden.
- Produktionszugangsdaten nur aus dem Secret-Store laden und nach Offenlegung beim jeweiligen Anbieter rotieren.
- CORS auf konkrete benötigte Origins beschränken.
- Datenbank-Backups und Wiederherstellung separat planen und regelmäßig testen.
- Auth0-Callbacks, Actions, Management-API-Berechtigungen und MFA vor der Staging-Freigabe prüfen.
