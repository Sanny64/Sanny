# Deployment

Dieses Projekt verwendet einen einfachen Release-Train für ein Monorepo mit:

- `sanny` Frontend.
- `login` Frontend.
- ...
- `docs` App.
- Fastify Backend.
- Shared Packages unter `shared/packages/**`.

Das Ziel ist es, `main` sehr sauber zu halten, eine echte Web-Testumgebung zu unterstützen und den Workflow für einen Solo-Entwickler einfach ausführbar zu machen.

---

## Branch-Modell

Dieses Projekt verwendet `dev -> test -> main`.

### `dev`

- Täglicher Entwicklungs-Branch.
- Feature-Arbeit landet zuerst hier.
- Die Commit-Historie kann unordentlich sein.
- Nichts in `dev` gilt als releasebereit, bis es nach `test` promotet wurde.

### `test`

- Release-Candidate-Branch.
- Deployed die öffentliche Testumgebung.
- Wird verwendet, um den exakten Release im Web vor Produktion zu verifizieren.
- Fixes für Release-Candidate-Probleme landen zuerst hier.

### `main`

- Ausschließlich Produktions-Branch.
- Wird sauber und gut lesbar gehalten.
- Wird nur durch Squash-Merges von `test` nach `main` aktualisiert.
- Jeder Release sollte genau einen kleinen Squash-Commit auf `main` erzeugen.

---

## Deployment-Zuordnung

### Testumgebung

Ein Push auf `test` deployed die öffentlich erreichbare (zukünftig login-geschützte) Testumgebung.

- `sanny` -> Testseite.
- `login` -> Testseite.
- Shared Packages werden bei Bedarf als Teil der Frontend-Pipeline gebaut.
- Backend-Test-Deployment ist vorläufig und kann manuell oder eingeschränkt bleiben, bis der Backend-Workflow finalisiert ist.

### Produktion

Ein Push auf `main` deployed die Produktion.

- `sanny` -> Produktionsseite.
- `login` -> Produktionsseite.
- `docs` -> Produktionsseite.
- Shared Packages werden bei Bedarf als Teil der Frontend-Pipeline gebaut.
- Backend-Produktions-Deployment ist derzeit vorläufig. Die Test- und Deployment-Pipeline löst Deployments derzeit nur aus, wenn sie manuell gestartet wird.

---

## Regel für Shared Packages

`shared/packages/**` beeinflusst immer Frontend-Builds.

Das bedeutet:

- Jede relevante Änderung in `shared/packages/**` muss die Frontend-Pipeline auslösen.
- Shared Packages werden nicht eigenständig manuell deployed.
- Wenn sich ein Shared Package ändert, muss das abhängige Frontend in Test und Produktion neu gebaut werden.

So bleibt der Shared Code synchron mit den Apps, die ihn verwenden.

## Release-Flow

### 1. Arbeit auf `dev` erstellen

- Erstelle einen Feature-Branch von `dev`.
  - `feat/<name>`
- Nimm deine Änderungen vor.
- Merge den Feature-Branch zurück in `dev`.

### 2. `dev` nach `test` promoten

- Wenn du einen Release-Candidate erstellen möchtest, merge `dev` in `test`.
- Pushe `test`.
- Die Testumgebung wird automatisch deployed.

### 3. Im Web testen

- Öffne die Testumgebung im Browser.
- Überprüfe UI, Integration, Deployment-Verhalten und backendabhängige Abläufe.
- Behebe Fehler, indem du von `test` branchst.

### 4. Release-Probleme auf `test` beheben

- Erstelle einen Fix-Branch von `test`.
  - `fix/<name>`
- Wende den Fix an.
- Merge den Fix zurück in `test`.
- Pushe `test` erneut, um die Testumgebung neu zu deployen.
- Sobald der Fix verifiziert ist, promote `test` nach `main` und merge `test` zurück in `dev`.

### 5. `test` nach `main` promoten

- Sobald die Testumgebung freigegeben ist, erstelle eine Pull Request von `test` nach `main`.
- Verwende Squash Merge.
- Dadurch entsteht ein sauberer einzelner Release-Commit auf `main`.

### 6. Produktions-Deployment

- Nach dem Squash Merge wird die Produktion von `main` deployed.
- Frontends und Docs deployen automatisch.
- Backend-Deployment benötigt einen manuellen `workflow_dispatch`-Trigger im GitHub-Actions-Menü.

## Schritt-für-Schritt Git-Leitfaden

### An einem Feature arbeiten

Erstelle einen Feature-Branch basierend auf dem dev-Branch:

```bash
git checkout dev
git pull origin dev
git checkout -b feat/<name>
```

Committe deine Arbeit und pushe den Branch:

```bash
git add .
git commit -m "Änderung beschreiben"
git push -u origin feat/<name>
```

Wenn fertig, merge ihn zurück in `dev`:

```bash
git checkout dev
git pull origin dev
git merge feat/<name>
git push origin dev
```

### Release-Candidate starten

Wenn `dev` bereit ist:

```bash
git checkout test
git pull origin test
git merge dev
git push origin test
```

Dies deployed die Testumgebung.

### Release testen

Nutze die öffentliche Testseite, um zu prüfen:

- Layout und UI.
- Routing.
- API-Verhalten.
- Änderungen an Shared Packages.
- Deployment-spezifische Probleme.

Wenn alles passt, weiter zur Produktion. Falls nicht, Fix auf `test` durchführen.

### Problem auf `test` beheben

Erstelle einen Bugfix-Branch basierend auf `test`:

```bash
git checkout test
git pull origin test
git checkout -b fix/<name>
```

Führe den Fix durch und merge ihn zurück in `test`:

```bash
git add .
git commit -m "Release-Problem beheben"
git checkout test
git pull origin test
git merge fix/<name>
git push origin test
```

Für alle Bugs wiederholen.  
Nachdem jeder Fix auf `test` validiert wurde und der Release stabil ist, merge `test` in `dev`.

```bash
git checkout dev
git pull origin dev
git merge test
git push origin dev
```

### Zur Produktion promoten

Wenn `test` freigegeben ist:

1. Erstelle eine Pull Request von `test` nach `main`.
2. Lass CI laufen.
3. Verwende Squash Merge.

So bleibt `main` sauber und enthält kompakte Release-Commits.

---

## Feature-Branches neu synchronisieren

Wenn Feature-Branches auseinanderdriften und wieder denselben Stand haben sollen, verwende `dev` als Integrationspunkt.

1. Merge alle Feature-Branches lokal in `dev` (in Abhängigkeitsreihenfolge, um Konflikte zu vermeiden).
2. Pushe `dev`.
3. Ziehe oder merge `dev` in jeden Feature-Branch, um zu synchronisieren.
4. Pushe die aktualisierten Feature-Branches.

Dies ist ein Recovery-Schritt über den normalen `dev`-Integrations-Branch. Er ist hilfreich, wenn mehrere Branches von denselben Shared-Package- oder Workspace-Änderungen abhängen und lokale Dev-Server wieder konsistent laufen sollen.

---

## Produktions-Deploy-Verhalten

Das Produktions-Deployment startet von `main` nach dem Squash Merge.

- `sanny` wird aus dem `main`-Branch deployed.
- `login` wird aus dem `main`-Branch deployed.
- ... wird aus dem `main`-Branch deployed.
- `docs` wird aus dem `main`-Branch deployed.
- Änderungen in Shared Packages triggern je nach Branch ebenfalls die Frontend-Release-Pipeline.
- Backend-Produktions-Deployment ist vorläufig.
  - Es sollte nur manuell ausgelöst werden, wenn alles bereit ist (VPS-Secrets gesetzt etc.).

Damit ist `main` die Quelle der Wahrheit für Produktion, während die Release-Historie klein und sauber bleibt.

---

## Backend-Hinweis

Das Backend-Deployment ist aktuell vorläufig.

Das bedeutet:

- Es sollte nicht den gesamten Release-Train bestimmen.
- Es kann manuell bleiben, bis der Backend-Workflow vollständig definiert ist.
  - VPS-Host ausgewählt, Server-Setup etc.; aktuell bleibt das Backend nur lokal verfügbar
- Frontend- und Docs-Releases sollten weiterhin dem normalen `dev -> test -> main`-Pfad folgen, unabhängig vom Backend-Status.
